Deadlocking a DEF CON 34 Badge Over USB

Deadlocking a DEF CON 34 Badge Over USB

How reading four thousand files found nothing, and a fuzzer running for ninety seconds found the bug.

That skull is not supposed to be able to stay on that screen. Getting it to stay is the whole story, and it took a lot longer than the ninety seconds implies.

The invitation

The DEF CON 34 badge is a hardware security key. Not a toy shaped like one — an actual FIDO2 token with a password manager and a TOTP store, built around an open-source RISC-V SoC, running a pure-Rust microkernel OS, with the CPU design itself published.

The badge program does something unusual with that. It doesn’t say “please don’t break this.” It says the opposite:

There’s a single, symmetric pre-shared key among all the badges: can you break the badge’s security and extract the key? In theory, the firmware on the badge is locked down. You’re invited to hack on the badge, but loading code “through the front door” will erase the pre-shared key. Don’t like that? I’m counting on some clever hackers at DEF CON finding other ways in!

There’s a trap in that paragraph, and it’s the reason this project was interesting rather than trivial. Loading your own firmware is supported — there’s a documented path for it. Taking that path trips erase_secrets(), a one-way door that wipes the provisioned key material. So the front door is open, and walking through it destroys the thing you came for. Anything worth finding has to come in some other way.

The hardware you’re attacking:

A 350 MHz RV32-IMAC application core with an MMU, four 700 MHz I/O coprocessors, 2 MiB SRAM, 4 MiB of on-chip RRAM, hardware crypto accelerators, a TRNG, glitch sensors, an anti-tamper mesh. Secure boot with post-quantum signatures. It is a genuinely serious design, published in full — which cuts both ways, because everything defending it is readable, and so is everything wrong with it.

Where to look, and being wrong about it

Eleven repositories. Roughly four thousand files. Auditing evenly would have burned the whole engagement, so the work started with a bet:

Novel defects live in code written for this badge, on a conference deadline. They don’t live in the upstream FIDO stack, which has been fuzzed for years, or in the upstream OS core.

That produced a priority order: the badge-specific application layer first, then the SoC’s published hardware description, then the bootloader, then secure boot last — highest value if broken, but certainly the most hardened.

The bet was reasonable. It was also not what found the bug. Worth saying plainly up front, because write-ups usually present the reasoning that worked and quietly drop the reasoning that didn’t.

Dead end one: the light protocol

The badge’s headline feature is exchanging light patterns with other attendees by scanning QR codes, with the exchange encrypted. The wire format reconstructs cleanly from source:

Every obvious attack was already handled. Nonce reuse degrades only to equality leakage, because GCM-SIV is misuse-resistant — a deliberate, correct choice. Confusing the header for a nonce is explicitly rejected in the nonce generator. Short-plaintext indexing is bounded: the guard requires ciphertext ≥ 32 bytes, the cipher strips a 16-byte tag, so the plaintext is always at least 16 and the indexed accesses are in range.

The conclusion at the time — “everything is gated on the shared key, so this isn’t an entry point” — was correct with the wrong reasoning. The key had already been published, with the designer’s blessing. It gates nothing. All of this was prior art and the entire branch was wasted effort.

Lesson, applied to everything afterwards: check what’s already public before auditing, not after.

Dead end two: secure boot

The signature checker is the highest-value target in the tree. Break it and you load unsigned firmware without tripping the wipe.

It’s also the most defended code in the tree: tripwire macros between every step, CSPRNG-driven delays, revocation counters duplicated at a fixed offset, verdict constants stored alongside their own complements, an XOR-masked jump target.

Three specific attacks, all dead:

  1. A “paranoid” re-check compares against a hardcoded tag while the first check uses a table lookup. If those differed, the second check would be dead code and the whole redundancy would be theatre. They’re the same value.
  2. Two adjacent lines write (!key_inv) == DEV and !key_inv == DEV — the second without parentheses. In C that’s a precedence bug. In Rust unary ! binds tighter than ==, and on a usize it’s bitwise, so both parse identically. Nice try.
  3. An index computed as offset + i - DUPE_DISTANCE looked like it could underflow. There’s already an invariant table asserting the relationship holds for all three partitions.

Attacking this properly means fault injection, and there was no glitcher on hand. Rather than write speculative analysis about an attack that couldn’t be attempted, the honest move was to stop.

Dead end three: reading hardware

The SoC’s register-transfer-level source is published, and almost nobody greps published RTL looking for bugs — everyone treats it as documentation. That seemed like an edge.

It half was. Two real asymmetries turned up. A DMA address filter has two instances, memory and peripheral, and the port map passes the memory instance’s disable bit to both. A register write-lock primitive is used with real conditions in the crypto blocks and tied to a constant zero in the three security-sensor blocks — the ones that detect glitching — leaving their configuration writable forever.

Both are real readings. Neither was ever demonstrated on the badge. The filter miswiring fails safe in the shipped configuration, so there is nothing observable to show. The write-lock observation is a precondition for fault injection, which was precisely the thing there was no equipment for.

They’re not in the final report. Reading code and concluding a bug exists is not the same as showing one, and a report that mixes the two is worth less than one that doesn’t.

The turn: hardware disagrees with the reading

Static review said the console’s chunk parsers were clean. Indices bounds-checked before use, exact-fit arithmetic, pin values masked before shifting. Nothing there.

The plan was to confirm that on silicon and move on. A fuzzer, 240 malformed inputs at the image and code-upload chunk parsers: truncated frames, wrong checksums, out-of-range indices, oversized payloads, bad base64, colliding indices.

239 rejected cleanly. The static review was right about the parsers.

Case 10 killed the device.

Not crashed — killed. Console stopped answering. Buttons stopped responding. The display froze mid-frame. Unplugging and replugging USB brought the port back and the device still didn’t answer. Only pulling power entirely recovered it.

First explanation: wrong

Case 10 sent a 4096-byte line. Obvious conclusion: long lines break the input path.

A bisector was written to prove it — walk 64 → 4096 characters, one command at a time, pause between each, liveness check after each.

Every single length survived. Including 4096, the exact payload that had just bricked the thing.

That tool is still in the repo (attack bisect) even though it proves a negative, because the negative is the interesting part: the obvious hypothesis is wrong, and anyone reproducing this will form it too.

Second explanation: right

The fuzzer and the bisector sent identical bytes. What differed was pacing — the fuzzer had no delay between cases.

Reproducible. The trigger is sustained throughput, not any individual message.

The mechanism

Three files. Each individually reasonable. Together, a device you can’t turn back on.

1. An unbounded loop over attacker-controlled input, inside a message handler:

The USB server can’t service anything else until that returns, and the peer decides how long it runs.

2. inject_key uses the blocking send:

When the keyboard server’s queue is full, the caller sleeps until there’s room. No rate limit, no non-blocking variant on this path.

3. Delivery to listeners is lossy:

And there’s the asymmetry that is the entire bug:

Direction Send form When the queue is full
Injected key (USB → keyboard server) send_message blocks — backpressure upstream
Delivered key (keyboard server → listener) try_send_message drops — and continues

Backpressure only travels backwards. The USB server absorbs it and stalls. The listeners — the security UI, the console — never feel it; their events are simply discarded.

So the attacker’s traffic gets a polite retry loop, and the user’s button press gets thrown in the bin.

That’s why flooding a USB port kills the physical buttons. Button events and injected characters converge on the same server, and only one of the two is allowed to wait.

What I couldn’t explain, and the answer

One thing didn’t fit. This SoC has a watchdog. A hung system should reset.

I reported the finding to the badge team with that gap left open, and the designer filled it in:

The hang I think happens because the system is in deadlock. If dependent servers’ message queues fill up, you can enter a deadlock situation and none of the user processes can make progress. Probably what’s happening though is that the power manager process (responsible for walking the watchdog) does still make progress, which is why that doesn’t trigger — the problem is that this manifests as deadlock and not as a panic (which would stop kernel scheduling and thus lead to a reboot).

That is a much better answer than the one I had, and it changes the shape of the finding.

A microkernel like this is built to survive two failure modes. A panic stops kernel scheduling, the watchdog stops being fed, the chip reboots. A hang in one server leaves the others running.

This is neither. It’s a mutual wait among dependent servers, so every user process stops — while the power manager, which isn’t in that dependency cycle, keeps cheerfully walking the watchdog. The hardware’s last-resort recovery is actively suppressed by a process that is working exactly as designed.

The failure mode is precisely the one that falls between the two the system defends against.

Making it visible

A deadlocked device photographs as a stopped screen. That proves nothing to a reader, so the finding needed a sharper demonstration — and the firmware supplied one by trying to prevent it.

The badge lets you upload a bitmap over the console. It also refuses to let that bitmap stay:

Every three seconds, hardcoded, no setting to disable it, your image is swapped back for the DEF CON logo. Deliberate — the badge always returns to showing what it is.

So the demonstration is two steps, and being honest about the split is the whole point:

  1. Upload a picture using the documented console command. This is not an exploit. The official tooling does exactly this. Anyone can do it.
  2. Trigger the deadlock while that picture is the frame on the panel. The UI stops redrawing. The OLED holds its last frame indefinitely.

Step 1 is the vendor’s API. Step 2 is the defect. Putting a picture on the screen proves nothing. Keeping it there, against code specifically written to prevent that, is the part that requires the bug.

That’s the skull at the top of this post. It survived a reboot attempt. It came off when the batteries did.

Getting it legible took three tries, all defeated by the same thing: the UI renders user bitmaps through an error-diffusion dither. Scaled font glyphs dissolve into noise. One-pixel outlines dissolve. Two-pixel whiskers dissolve. What survives is solid filled mass with features punched out as holes — which is why the final art looks like a woodcut instead of a drawing.

What the vendor said, including the unflattering half

The response was better than the finding deserved, and quoting only the agreeable parts would misrepresent it.

On the fix:

Thanks! Adding backpressure on the USB console input loop is probably a good idea.

On severity — and they’re right:

I don’t consider this to be a particularly scary DoS (at least for us), since the attacker would need to be able to run a program on the host targeting the dongle, at which point they have fairly significantly escalated privileges overall (that is, this isn’t quite like a server sitting on the internet where anyone can just send a packet to it).

That’s the correct framing. Unauthenticated to the device is not the same as unauthenticated to the world. An attacker who can already run code on your machine has better options than freezing your badge. The device-level impact is real — no pairing, no button press, permanent until power loss, defeats the watchdog — but that’s a different axis from what it’s worth to an attacker in practice.

And the part that puts the whole thing in proportion:

However, you are correct that the console input path over USB is pretty sketchy — it’s mostly a convenience for debug/development. On that note, for production devices that are solely intended to be security tokens, they would actually ship with the console entirely turned off, because it wouldn’t make sense to even make the attack surface available on a security token.

The mitigation already exists. The badge is the development-convenience build; the security-token build doesn’t expose this surface at all.

What generalises

The bug was found by a tool built to confirm the absence of bugs. The parser fuzzer’s purpose was to validate a clean static review. It did — 239 of 240 inputs rejected correctly. The finding came from the side effect nobody was testing for: not what the parser did with the bytes, but what the transport underneath it did with their arrival rate.

The obvious hypothesis was wrong and cost a day. “Long line breaks it” was disproven by a tool written to prove it. If the bisector had been skipped as unnecessary, the report would have shipped with the wrong root cause and the wrong fix.

Mixed blocking and non-blocking sends across a trust boundary is a bug pattern, not an incident. Blocking one way, dropping the other, means backpressure only ever propagates towards the victim. The attacker gets a retry loop, the legitimate user gets dropped. Worth grepping for anywhere a message queue has an external peer on one side and a user on the other.

A fix for the trigger isn’t a fix for the class. Bounding that one loop removes this path. Any other path that fills a dependent server’s queue faster than it drains reaches the same deadlock — and the watchdog will miss that one too, for the same reason. The general answer is either detecting mutual waits, or having whatever feeds the watchdog able to observe that no user process is making progress.

Cut what you didn’t demonstrate. This engagement produced seven candidate defects. Six came from reading source and hardware descriptions; exactly one was fired at the badge and worked. The final report contains one finding. The other six were interesting, plausible, and unproven, and shipping them alongside a verified result would have devalued the verified result. If it didn’t run on the hardware, it doesn’t go in.

Timeline

Wrong hypothesis, disproven by bisector length is not the trigger

Log string → source → author’s own comment mechanism confirmed
Reported to badge team acknowledged; deadlock explanation supplied
Published this post, plus an OS issue with the PoC attached

One note on that 2,900 figure: it’s real for the unit measured and it is not a constant. A freshly power-cycled badge later absorbed 90,000 characters at the same rate without flinching. The threshold depends on how much state has accumulated — listeners registered, queues partially filled. The released tooling measures the unit in front of you rather than trusting the number above.

Reproducing it

Recovery is always the same: remove power. Unplug USB with no batteries fitted, or pull a cell. The badge freezing is the finding working, not the tool misbehaving.

Everything goes through a transport layer that makes each tool declare the console verbs it needs and enforces a hard denylist underneath that no tool can opt out of — the destructive verbs, the firmware writers, and anything that burns a one-way counter that no backup can restore. Nothing in the released toolkit writes flash.
