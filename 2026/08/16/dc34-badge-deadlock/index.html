Deadlocking a DEF CON 34 Badge Over USB

I brought the badge home from Las Vegas without a plan. Weeks of reading source found nothing. Then a fuzzer I’d written to prove there was nothing there bricked the device on its tenth case, ninety seconds in.

That skull isn’t supposed to be able to stay on that screen. The firmware wipes it every three seconds. Getting it to stay is the whole story, and it took a lot longer than ninety seconds.

Coming home with a badge

I went to DEF CON 34 in Las Vegas. I came back to Taiwan with the usual pile of stickers, a wrecked sleep schedule, and the badge.

The badge is the interesting part. It’s not a toy shaped like a security key. It’s an actual FIDO2 hardware token with a password manager and a TOTP store, built on an open-source RISC-V SoC, running a pure-Rust microkernel OS, with the CPU design itself published.

And the badge program does something unusual with that. It doesn’t say please don’t break this. It says the opposite:

There’s a single, symmetric pre-shared key among all the badges: can you break the badge’s security and extract the key? In theory, the firmware on the badge is locked down. You’re invited to hack on the badge, but loading code “through the front door” will erase the pre-shared key. Don’t like that? I’m counting on some clever hackers at DEF CON finding other ways in!

There’s a trap buried in that paragraph, and it’s what makes the target interesting instead of trivial. Loading your own firmware is supported. There’s a documented path for it. Take that path and you trip erase_secrets(), a one-way door that wipes the provisioned key material. The front door is wide open, and walking through it destroys the thing you came for. Anything worth finding has to arrive some other way.

None of this happened in Vegas. The laptop I travel with isn’t my personal machine, so it’s not somewhere I’m willing to do attack research. The badge went into a bag and the work waited until I was home in front of a real desk.

Which, in hindsight, is the only reason this finding exists at all. The bug needs a host that can push thousands of characters per second down a USB serial pipe without stuttering, and it needs the patience to power-cycle a dead device dozens of times in a row. Neither of those is something you do standing up in a hallway.

The hardware being attacked:

https://github.com/baochip/baochip-1x/blob/main/docs/src/images/soc-top-diagram.png

A 350 MHz RV32-IMAC application core with an MMU, four 700 MHz I/O coprocessors, 2 MiB of SRAM, 4 MiB of on-chip RRAM, hardware crypto accelerators, a TRNG, glitch sensors, an anti-tamper mesh. Secure boot with post-quantum signatures. It’s a serious design and it’s published in full, which helps both sides: everything defending it is readable, and so is everything wrong with it.

Repositories, an AI partner

This is where I leaned on Claude, and I want to be exact about how, because “AI found a 0day” isn’t what happened here and the real split of labour is more useful to anyone trying to repeat it.

What the AI was good for. Bulk reading. Point it at a crate and ask where does attacker-controlled length reach an unbounded loop, or which of these two send primitives blocks, or find every register bit declared in the SVD that the RTL claiming to own it never reads. Questions where the answer is a list of file/line candidates and a false positive costs me one minute of reading. It kept that up across four thousand files. I couldn’t have.

What it was bad for. Deciding whether any of those candidates matter. Left alone it writes confident advisories for things that turn out to be defended two files away, or that fail safe in the shipped configuration, or that nothing reachable can trigger. Every lead in this section arrived looking like a finding, and every one of them died when I sat down with the source, or with the badge, and checked.

The prompt

The highest-leverage thing I did on this whole project was spend an evening writing the prompt instead of chatting with the model. No clever prompt-engineering. Just doing the recon myself first, then handing over a target description that was already correct, already scoped, and already had the closed doors marked closed.

Condensed, that prompt was:

Three things in there did most of the work, and none of them are about the model.

The “already closed” list. Community write-ups already existed. Pasting the closed paths in, along with the reason each one is closed, is what kept the model from burning its context rediscovering the empty BDMA whitelist and handing it back to me as a finding. It still had to verify those claims. It just didn’t have to find them.

“Verify on hardware, or label it a hypothesis.” That single line is the difference between a report and a stack of plausible prose. It’s also the instruction the model was worst at following on its own. Left unattended, an LLM will happily write you an advisory for something it inferred from two files and never touched. I ended up enforcing this by hand, every single time.

And the diary. Requiring failures to be written down as they happened, instead of summarised at the end, is what made the dead-end sections of this post possible. It also caught a genuine mistake of mine: the diary shows me closing the light-protocol branch for the wrong reason, which is only visible because the wrong reasoning got recorded at the time instead of tidied away afterwards.

Hardware disagrees with the reading

Static review said the console’s chunk parsers were clean. Indices bounded, arithmetic exact, pin values masked before shifting.

By that point in the project, though, I’d stopped trusting that verdict on its own. The light protocol and the bootloader had both looked clean on paper and been clean. But the RTL read had thrown off two hypotheses that no amount of further reading could settle, only hardware could. So instead of moving on, I decided to confirm the parser verdict on silicon.

I wrote a fuzzer. 240 malformed inputs aimed at the image and bio chunk parsers: truncated frames, wrong CRCs, out-of-range indices, oversized payloads, bad base64, colliding indices.

239 rejected cleanly. The static review was right about the parsers.

Case 10 killed the device.

Not crashed. Killed. The console stopped answering. The buttons stopped responding. The display froze mid-frame. Unplugging and replugging USB brought the port back, and the device still said nothing. Only pulling power entirely brought it back.

First explanation: wrong

Case 10 sent a 4096-byte line. Obvious conclusion: long lines break the input path.

I wrote a bisector to prove it. Walk 64 → 4096 characters, one command at a time, pause between each, liveness check after each.

Every single length survived. Including 4096, the exact payload that had bricked the thing twenty minutes earlier.

That tool is still in the repository (attack bisect) even though all it proves is a negative, because the negative is the useful part: the obvious hypothesis is wrong, and anyone reproducing this will land on it too.

Second explanation: right

The fuzzer and the bisector sent identical bytes. The difference was pacing. The fuzzer had no delay between cases.

A rate ramp tests that variable directly: fixed payload, increasing sustained throughput, liveness check between steps.

Reproducible. The trigger is sustained throughput, not any individual message.

The mechanism

Three files. Each one individually reasonable. Together, a device you can’t turn back on.

1. An unbounded loop over attacker-controlled input, inside a message handler (services/usb-bao1x/src/main.rs:610):

The USB server can’t service anything else until that returns, and the peer decides how long it runs for.

2. inject_key uses the blocking send (services/keyboard/src/lib.rs:106):

When the keyboard server’s queue is full, the caller sleeps until there’s room. No rate limit, no non-blocking variant anywhere on this path.

3. Delivery to listeners is lossy (services/bao1x-hal-service/src/servers/keyboard.rs:492):

And there’s the asymmetry that constitutes the whole bug:

Direction Send form When the queue is full
Injected key (USB → keyboard server) send_message blocks — backpressure upstream
Delivered key (keyboard server → listener) try_send_message drops — and continues

Backpressure only travels backwards. The USB server absorbs it and stalls. The listeners, meaning the vault UI and the console, never feel a thing; their events are quietly discarded.

So the attacker’s traffic gets a polite retry loop, and the user’s button press goes in the bin.

That’s why flooding a USB port kills the physical buttons. Button events and injected characters converge on the same server, and only one of the two is allowed to wait.

What I could not explain, and the answer

I reported the finding to the badge team with that gap left open rather than papering over it. I’d recommend that to anyone doing this kind of work: don’t invent an explanation for something you can’t observe. Send the gap along as part of the report.

The hang I think happens because the system is in deadlock. If dependent servers’ message queues fill up, you can enter a deadlock situation and none of the user processes can make progress. Probably what’s happening though is that the power manager process (responsible for walking the watchdog) does still make progress, which is why that doesn’t trigger — the problem is that this manifests as deadlock and not as a panic (which would stop kernel scheduling and thus lead to a reboot).

That’s a far better answer than the one I had, and it changes the shape of the finding.

Some background on why the badge doesn’t just reboot itself. A watchdog is a hardware timer that resets the device unless the software keeps poking it, an “are you still alive?” check on a fixed interval. On this badge, the power manager does the poking.

A microkernel like this is built to survive two failure modes. A panic stops kernel scheduling, the watchdog stops being fed, the chip reboots. A hang in one server leaves everything else running.

This is neither. It’s a mutual wait between dependent servers, so every user process stops. Meanwhile the power manager, which sits outside that dependency cycle, keeps cheerfully walking the watchdog.

The hardware’s last-resort recovery is being actively suppressed by a process working exactly as designed.

The failure mode lands in the gap between the two cases the system defends against. That’s why nothing recovers it, and why the device stays dead indefinitely instead of resetting after a few seconds.

Making it visible

A deadlocked device photographs as a stopped screen, which proves nothing to a reader. The finding needed a sharper demonstration, and the firmware handed me one by trying to prevent it.

The badge lets you upload a bitmap over the console. It also refuses to let that bitmap stay (dc34-vault/src/ux.rs:783):

Every three seconds, hardcoded, with no setting to disable it, your image gets swapped back for the DEF CON logo. That’s deliberate. The badge always returns to showing what it is.

So the demonstration is two steps, and being honest about where the line falls between them matters more than the demo itself:

  1. Upload a picture using the documented image console command. This is not an exploit. The vendor’s own apply_image.py does exactly this. Anyone can do it.
  2. Trigger the deadlock while that picture is the frame on the panel. The vault stops redrawing. The OLED holds its last frame indefinitely.

Step 1 is the vendor’s API. Step 2 is the defect. Putting a picture on the screen proves nothing. Keeping it there, against code written specifically to prevent that, is the part that needs the bug.

The image survives a reboot attempt. It comes off when the batteries do.

Getting it legible took three tries, all defeated by the same thing: the vault renders user bitmaps through bitmap_diffusion, an error-diffusion dither. Scaled font glyphs dissolve into noise. One-pixel outlines dissolve. Two-pixel whiskers dissolve. What survives is solid filled mass with the features punched out as holes, which is why the final art looks like a woodcut instead of a drawing, and why the text scale is capped at 3.0 in the tooling.

Disclosure

Nothing here was published before it was reported. The finding went to the badge team first, through the normal channel, and everything in this post is public because they agreed it could be.

The response was better than the finding deserved, and quoting only the agreeable half would misrepresent it.

On the fix:

Thanks! Adding backpressure on the USB console input loop is probably a good idea.

On severity, where they’re right:

I don’t consider this to be a particularly scary DoS (at least for us), since the attacker would need to be able to run a program on the host targeting the Baochip dongle, at which point they have fairly significantly escalated privileges overall (that is, this isn’t quite like a server sitting on the internet where anyone can just send a packet to it).

Unauthenticated to the device isn’t the same as unauthenticated to the world. An attacker who can already run code on your machine has better things to do than freeze your badge. The device-level impact is real enough (no pairing, no button press, permanent until power loss, defeats the watchdog) but that’s a separate axis from what it’s actually worth to an attacker.

And the part that puts the whole thing in proportion:

However, you are correct that the console input path over USB is pretty sketchy — it’s mostly a convenience for debug/development. On that note, for production devices that are solely intended to be security tokens, they would actually ship with the console entirely turned off, because it wouldn’t make sense to even make the attack surface available on a security token.

Reproducing it

https://github.com/Trinity-SYT-SECURITY/defcon-badge-0day

Recovery is always the same: remove power. Unplug USB with no batteries fitted, or pull a cell. A frozen badge means the finding is working, not that the tool is broken.

Every command goes through a transport layer that makes each tool declare the console verbs it needs, and enforces a hard denylist underneath that no tool can opt out of: the destructive verbs (self_destruct, lockdown, publock), the firmware writers (uf2, uf2_flush), and anything that burns a one-way counter no backup can restore. Nothing in the released toolkit writes flash.

Note: loading your own code onto the badge causes it to enter developer mode. If I understand correctly…This is a one-way door which causes provisioned secrets to be erased. Nothing in the released toolkit triggers this, but it’s worth knowing before you start experimenting.
