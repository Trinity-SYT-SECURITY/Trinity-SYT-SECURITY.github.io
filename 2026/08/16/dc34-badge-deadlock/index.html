Deadlocking a DEF CON 34 Badge Over USB

I brought the badge home from Las Vegas without a plan. Many files of reading found nothing. A fuzzer that ran for ninety seconds — written to prove there was nothing there — bricked the device on its tenth case.

That skull is not supposed to be able to stay on that screen. The firmware actively removes it every three seconds. Getting it to stay is the whole story, and it took a great deal longer than ninety seconds.

Coming home with a badge

I went to DEF CON 34 in Las Vegas. I came back to Taiwan with the usual pile of stickers, a bad sleep schedule, and the badge.

The badge is the interesting part. It is not a toy shaped like a security key — it is an actual FIDO2 hardware token with a password manager and a TOTP store, built around an open-source RISC-V SoC, running a pure-Rust microkernel OS, with the CPU design itself published.

The badge program does something unusual with that. It does not say please don’t break this. It says the opposite:

There’s a single, symmetric pre-shared key among all the badges: can you break the badge’s security and extract the key? In theory, the firmware on the badge is locked down. You’re invited to hack on the badge, but loading code “through the front door” will erase the pre-shared key. Don’t like that? I’m counting on some clever hackers at DEF CON finding other ways in!

There is a trap in that paragraph, and it is what makes the target interesting rather than trivial. Loading your own firmware is supported, there is a documented path. Taking that path trips erase_secrets(), a one-way door that wipes the provisioned key material. So the front door is open, and walking through it destroys the thing you came for. Anything worth finding has to arrive some other way.

I did not do any of this in Vegas. The laptop I brought to Las Vegas isn’t my personal one, so it’s not really suitable for conducting any kind of attack research on it. So the badge went into a bag and the work waited until I was back home in front of a real machine.

Which, in hindsight, is the only reason this finding exists. The bug requires a host that can sustain thousands of characters per second down a USB serial pipe without stuttering, and it requires the patience to power-cycle a frozen device dozens of times. Neither is something you do standing up in a hallway.

The hardware being attacked:

https://github.com/baochip/baochip-1x/blob/main/docs/src/images/soc-top-diagram.png

A 350 MHz RV32-IMAC application core with an MMU, four 700 MHz I/O coprocessors, 2 MiB of SRAM, 4 MiB of on-chip RRAM, hardware crypto accelerators, a TRNG, glitch sensors, an anti-tamper mesh. Secure boot with post-quantum signatures. A genuinely serious design, published in full — which cuts both ways, because everything defending it is readable, and so is everything wrong with it.

Repositories, an AI partner

This is where I leaned on Claude, and it is worth being precise about how, because “AI found a 0day” is not what happened and the real division of labour is more useful to anyone trying to repeat it.

What the AI was good for. Bulk reading. Pointing it at a crate and asking where does attacker-controlled length reach an unbounded loop, which of these two send primitives blocks, find every register bit declared in the SVD that is never read by the RTL that claims to own it — questions where the answer is a list of file/line candidates and the cost of a false positive is one minute of my own reading. It sustained that across four thousand files in a way I could not have.

What it was bad for. Deciding whether any of those candidates matter. Left to itself it produces confident write-ups for things that turn out to be defended two files away, or fail safe in the shipped configuration, or are unreachable. Every single lead in this section came back looking like a finding and was killed by me sitting down with the source, or with the badge, and checking.

The brief

The single highest-leverage thing I did in this whole project was spend an evening writing the brief instead of chatting with the model. Not prompt-engineering tricks — just doing the recon myself first and handing over a target description that was already correct, already scoped, and already had the closed doors marked closed.

Condensed, that brief was:

Three things in there did most of the work, and none of them are about the model.

The “already closed” list. Community write-ups already existed. Pasting the closed paths in — with the reason each one is closed — is what stopped the model from spending its context rediscovering the empty BDMA whitelist and presenting it to me as a finding. It still had to verify the claims, but it did not have to find them.

“Verify on hardware, or label it a hypothesis.” This one line is the difference between a report and a pile of plausible prose. It is also the one the model was worst at obeying unprompted — left alone, an LLM will write you a confident advisory for something it inferred from two files and never touched. I ended up enforcing it manually, every time.

Requiring the failures to be written down as they happened, rather than a summary at the end, is what makes the dead-end sections of this post possible. It also caught a real mistake: the diary shows the light-protocol branch being closed for the wrong reason, which is only visible because the wrong reasoning was recorded at the time instead of being tidied away.

Hardware disagrees with the reading

Static review said the console’s chunk parsers were clean. Indices bounds-checked before use, exact-fit arithmetic, pin values masked before shifting. Nothing there.

The plan was to confirm that on silicon and move on. I wrote a fuzzer — 240 malformed inputs aimed at the image and bio chunk parsers: truncated frames, wrong CRCs, out-of-range indices, oversized payloads, bad base64, colliding indices.

239 rejected cleanly. The static review was right about the parsers.

Case 10 killed the device.

Not crashed — killed. The console stopped answering. The buttons stopped responding. The display froze mid-frame. Unplugging and replugging USB brought the port back and the device still did not answer. Only pulling power entirely recovered it.

First explanation: wrong

Case 10 sent a 4096-byte line. Obvious conclusion: long lines break the input path.

I wrote a bisector to prove it — walk 64 → 4096 characters, one command at a time, pause between each, liveness check after each.

Every single length survived. Including 4096, the exact payload that had just bricked the thing.

That tool is still in the repository (attack bisect) even though all it proves is a negative, because the negative is the interesting part: the obvious hypothesis is wrong, and anyone reproducing this will form it too.

Second explanation: right

The fuzzer and the bisector sent identical bytes. What differed was pacing — the fuzzer had no delay between cases.

A rate ramp tests that variable directly: fixed payload, increasing sustained throughput, liveness check between steps.

Reproducible. The trigger is sustained throughput, not any individual message.

The mechanism

Three files. Each individually reasonable. Together, a device you cannot turn back on.

1. An unbounded loop over attacker-controlled input, inside a message handler — services/usb-bao1x/src/main.rs:610:

The USB server cannot service anything else until that returns, and the peer decides how long it runs.

2. inject_key uses the blocking send — services/keyboard/src/lib.rs:106:

When the keyboard server’s queue is full, the caller sleeps until there is room. No rate limit, no non-blocking variant on this path.

3. Delivery to listeners is lossy — services/bao1x-hal-service/src/servers/keyboard.rs:492:

And there is the asymmetry that is the entire bug:

Direction Send form When the queue is full
Injected key (USB → keyboard server) send_message blocks — backpressure upstream
Delivered key (keyboard server → listener) try_send_message drops — and continues

Backpressure only travels backwards. The USB server absorbs it and stalls. The listeners — the vault UI, the console — never feel it; their events are simply discarded.

So the attacker’s traffic gets a polite retry loop, and the user’s button press gets thrown in the bin.

That is why flooding a USB port kills the physical buttons. Button events and injected characters converge on the same server, and only one of the two is allowed to wait.

What I could not explain, and the answer

I reported the finding to the badge team with that gap left open rather than papering over it, and the designer filled it in:

The hang I think happens because the system is in deadlock. If dependent servers’ message queues fill up, you can enter a deadlock situation and none of the user processes can make progress. Probably what’s happening though is that the power manager process (responsible for walking the watchdog) does still make progress, which is why that doesn’t trigger — the problem is that this manifests as deadlock and not as a panic (which would stop kernel scheduling and thus lead to a reboot).

That is a much better answer than the one I had, and it changes the shape of the finding.

A microkernel like this is built to survive two failure modes. A panic stops kernel scheduling, the watchdog stops being fed, the chip reboots. A hang in one server leaves the others running.

This is neither. It is a mutual wait among dependent servers, so every user process stops — while the power manager, which is not in that dependency cycle, keeps cheerfully walking the watchdog. The hardware’s last-resort recovery is actively suppressed by a process that is working exactly as designed.

The failure mode falls precisely between the two the system defends against. That is why nothing recovers it, and why the device stays dead indefinitely instead of resetting after a few seconds.

Making it visible

A deadlocked device photographs as a stopped screen, which proves nothing to a reader. So the finding needed a sharper demonstration — and the firmware supplied one by trying to prevent it.

The badge lets you upload a bitmap over the console. It also refuses to let that bitmap stay (dc34-vault/src/ux.rs:783):

Every three seconds, hardcoded, no setting to disable it, your image is swapped back for the DEF CON logo. Deliberate — the badge always returns to showing what it is.

So the demonstration is two steps, and being honest about the split is the entire point:

  1. Upload a picture using the documented image console command. This is not an exploit. The vendor’s own apply_image.py does exactly this. Anyone can do it.
  2. Trigger the deadlock while that picture is the frame on the panel. The vault stops redrawing. The OLED holds its last frame indefinitely.

Step 1 is the vendor’s API. Step 2 is the defect. Putting a picture on the screen proves nothing. Keeping it there, against code specifically written to prevent that, is the part that requires the bug.

The image survives a reboot attempt. It comes off when the batteries do.

Getting it legible took three tries, all defeated by the same thing: the vault renders user bitmaps through bitmap_diffusion, an error-diffusion dither. Scaled font glyphs dissolve into noise. One-pixel outlines dissolve. Two-pixel whiskers dissolve. What survives is solid filled mass with features punched out as holes — which is why the final art looks like a woodcut instead of a drawing, and why the text scale is capped at 3.0 in the tooling.

Disclosure

Nothing here was published before it was reported. The finding went to the badge team first, through the normal channel, and everything in this post is public because they agreed it could be.

The response was better than the finding deserved, and quoting only the agreeable parts would misrepresent it.

On the fix:

Thanks! Adding backpressure on the USB console input loop is probably a good idea.

On severity — and they are right:

I don’t consider this to be a particularly scary DoS (at least for us), since the attacker would need to be able to run a program on the host targeting the Baochip dongle, at which point they have fairly significantly escalated privileges overall (that is, this isn’t quite like a server sitting on the internet where anyone can just send a packet to it).

Unauthenticated to the device is not the same as unauthenticated to the world. An attacker who can already run code on your machine has better options than freezing your badge. The device-level impact is real — no pairing, no button press, permanent until power loss, defeats the watchdog — but that is a different axis from what it is worth to an attacker in practice.

And the part that puts the whole thing in proportion:

However, you are correct that the console input path over USB is pretty sketchy — it’s mostly a convenience for debug/development. On that note, for production devices that are solely intended to be security tokens, they would actually ship with the console entirely turned off, because it wouldn’t make sense to even make the attack surface available on a security token.

Reproducing it

https://github.com/Trinity-SYT-SECURITY/Hack-DEFCON34-Badge

Recovery is always the same: remove power. Unplug USB with no batteries fitted, or pull a cell. The badge freezing is the finding working, not the tool misbehaving.

Everything goes through a transport layer that makes each tool declare the console verbs it needs and enforces a hard denylist underneath that no tool can opt out of — the destructive verbs (self_destruct, lockdown, publock), the firmware writers (uf2, uf2_flush), and anything that burns a one-way counter no backup can restore. Nothing in the released toolkit writes flash.

Note: loading your own code onto the badge causes it to enter developer mode. If I understand correctly…This is a one-way door which causes provisioned secrets to be erased. Nothing in the released toolkit triggers this, but it is worth knowing before you start experimenting.
