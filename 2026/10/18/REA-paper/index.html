Say Exactly How Much You Know: Dissecting an Evidence-Bearing Reverse-Engineering Server for AI Agents

The Missing Layer: What REA’s Evidence Architecture Reveals About Building AI Agents for Vulnerability Research

Abstract

Language-model agents can now drive reverse-engineering tools directly, but the usual tool surface (a decompiler console, a disassembler script, a debugger prompt) returns text that looks equally authoritative whether it was read out of a file, reconstructed by a decompiler, or guessed. An agent that cannot tell those apart will state all three with the same confidence. This paper dissects a local analysis server that takes the opposite position: every analysis answer is wrapped in an Evidence record whose identity is the hash of its own semantic content, which names the provider that produced it, declares how directly the fact was seen (observed, derived, inferred) and who stands behind it (shipped-artifact, controlled-replay, historical-reference, external-service, analyst-inference), and carries its own limitations inline. Questions the run could not settle are not dropped; they are appended to a revision-chained ledger of residual unknowns that later calls must cite correctly or be refused.

We reconstruct the system from its source and then exercise it. Over 1,012 recorded protocol calls against 27 artifact classes (native executables and shared libraries for four object formats, managed assemblies, mobile packages and a live Android device, script bundles and archives, bytecode modules, databases, captures, firmware, and live browser, Electron and Node runtimes) we called every one of the 207 advertised tools and obtained successful results from 178. Of the remaining 29, 27 are gated by the host: a GUI engine whose demo build refuses the bridge script, macOS-only utilities, and an unlicensed decompiler; the other two are a debugger close that could never be verified and a device bug-report collector that failed for a reason we did not resolve. We report where the design holds and where it costs: a decompiler cold start that ranges from 14 s for a 512-byte image to 827 s for an 8 MB Swift binary; a second deep provider, present only in a post-release checkout, that answers the same question in 4 s but with a far coarser dossier; a response budget that refuses a 60 MB comparison rather than truncating it; a cleanup fence that converts one unverifiable debugger detach into a refusal of every later open in the session; a request path that has no such refusal at all, so that a request of 10.1 MiB, against one of exactly 10 MiB that was answered normally, silently tears down the connection; and an advertised tool catalog that costs 3.09 MB of JSON Schema by default and 215 KB under two configuration switches: a 14× difference in the bytes an agent must read before its first call.

The contribution is not a new analysis technique. It is a measured account of what it costs, and what it buys, to make a reverse-engineering tool surface say exactly how much it knows. We close by mapping that design onto vulnerability-research agents, where the same refusal to over-claim is the difference between a triage-ready finding and a false report.

1. Introduction

1.1 The problem

A reverse-engineering session is a chain of claims of very different quality. “The ELF header says the entry point is at 0x1a40“ is a fact read out of bytes that were hashed before and after reading. “This function compares a buffer against a constant string” is a decompiler’s reconstruction, correct often enough to be useful and wrong often enough to matter. “This binary was built by the same toolchain as that one” may be an inference from a path fragment embedded in a read-only section. A human analyst keeps that gradient in their head. A language-model agent, handed three strings over a tool call, does not, unless the interface makes the gradient part of the data.

The gradient is not academic. An agent that treats a decompiler’s variable name as ground truth will write a report that reads like a finding. An agent that silently loses a timeout will claim coverage it never had. An agent that reuses an identifier after the server discarded the underlying record will cite something that no longer exists. Each of these is a failure of the interface, not of the model.

1.2 The system

The subject of this study is a local-only reverse-engineering server, distributed as an npm package, that speaks the Model Context Protocol (MCP) over stdio and additionally exposes a command-line interface over the same contracts. It advertises 207 tools, 153 CLI commands and 6 guided prompts. It owns no analysis engine of its own: decompilation, disassembly, debugging, instrumentation, packet dissection, firmware carving and protocol decoding are delegated to caller-supplied engines reached through purpose-built bridges, each with its own identity, resource and cleanup discipline.

Its central design decision is that no tool returns a bare value. Every analysis result is wrapped in an Evidence record, and that record is the unit of identity, transport, retention, comparison and verification in the system. Session, lifecycle, ledger and bundle operations return structured state rather than Evidence, but never a bare string: in our study 454 of the 679 successful tool calls carried an Evidence record, and the other 225 were operations of that second kind (§13.2).

1.3 Research questions

  • RQ1 (coverage). How much of a 207-tool surface can actually be exercised on one ordinary Linux host, and what does the remainder depend on?
  • RQ2 (identity). Does content-addressed Evidence behave as advertised: stable under irrelevant change, unstable under relevant change, and resistant to tampering?
  • RQ3 (honesty under failure). When analysis cannot complete, does the system refuse with a typed, actionable code, or degrade into a plausible-looking answer?
  • RQ4 (cost). What do these guarantees cost in wall-clock time, response size and advertised-schema bytes, and which costs are configurable?
  • RQ5 (composition). Do the verification tools built on top of Evidence (comparison, correlation, reconstruction claims, coverage ledgers) hold their stated epistemic line, or do they quietly upgrade consistency into proof?

1.4 Contributions

  1. A source-level reconstruction of the server’s request pipeline, session lifecycle, Evidence model, engine bridges, runtime-observation subsystems, projection layer, composed workflows, prompt and completion system, CLI adapter and self-testing apparatus, with the mechanisms stated precisely enough to be re-implemented or contested (§3–§11). This includes how each tool maps to a concrete engine call, what the first query pays for versus a warm one, and how projections and composed workflows compute their own coverage (§7.1–§7.2, §9.2, §10.1).

  2. An execution study over 1,012 recorded calls and 27 artifact classes, covering all 207 tools, all six prompts and every completion kind, with every call, argument, reply, notification stream and timing retained as a reproducible record (§12).

2. Background and positioning

2.1 Agent tool protocols

MCP is a JSON-RPC protocol in which a server advertises tools with JSON Schemas, and a client (typically an agent runtime) calls them with structured arguments and receives structured results. The protocol provides progress notifications bound to a caller-supplied token, request cancellation, and prompts the client can render. It does not provide an epistemic model: a result is a blob, and whatever the server says about its own certainty must be carried in that blob.

Three protocol-level facts shape everything in §4: the advertised catalog is sent in full before the first call; results travel through a stdio pipe with a finite receive buffer; and cancellation is advisory, so a server that owns processes must do its own cleanup bookkeeping.

2.2 Why “evidence” rather than “output”

The system under study takes the position that a reverse-engineering result has four separable parts: the bytes examined (identified by digest, not by path), the producer (engine and version, plus the exact parameters it ran with), the claim, and the epistemic status of the claim. Collapsing these into a text blob loses exactly the information an agent needs to calibrate. Keeping them separate makes several things possible that are otherwise unavailable: two results can be compared for equality without comparing prose; a result can be re-cited later without being re-run; and a verification tool can refuse a claim whose sources are too weak for the claim being made.

2.3 Related positions

Reproducible-build and software-bill-of-materials work attaches provenance to produced artifacts; this system attaches provenance to observations about artifacts, which is the dual problem. Sandbox and capability literature concerns what a tool may do; the discipline here is adjacent but distinct: it concerns what a tool may claim. Classical binary-analysis platforms expose their engines directly and leave calibration to the analyst. We are not aware of an equivalent published treatment of an agent-facing analysis surface with an explicit epistemic algebra, and we make no claim to have surveyed the field exhaustively; the point of §3–§8 is the mechanism, not priority.

3. System overview

Figure 1. Who calls, what the server does in order, and what it owns. The four stages are the order every call passes through; the arrows are the only message paths. Engines are supplied by the operator and run as children of the server, never attached to. The figure describes the published 6.5.0 release; the whole-program exporter exists only at the later commit fe2a398dd.

The server is a single process per client connection. Startup is deliberately ordered (§4.1): environment snapshot, configuration parse, session construction, optional target, transport, shutdown registration. Optional observation providers (browser CDP, Playwright browser scenarios, Electron CDP, active Electron, V8 Inspector) are loaded independently, and a provider that fails to load leaves its tools advertised but marked unavailable, with the load failure as the reason, without failing the server.

Four properties recur at every layer and are worth stating once:

  • Ownership is proven, not assumed. A process is REA’s only if a run token minted before launch is still readable in that process’s environment and its start identity is unchanged. A PID and an executable path are explicitly insufficient (§6).
  • Interpretation has exactly one owner. Consumers use the owner’s parsed facts rather than re-reading raw source. Identity values and display formatting are kept apart.
  • Unknown is a value. Nothing that could not be determined is reported as absent, foreign or aligned; it is reported as unknown, and often as a ledger entry (§5.4).
  • Refusal is a result. Every failure projects into one of 20 codes and 10 categories with a remediation string, and carries partial observations where any exist (§4.6).

4. The request pipeline

4.1 Boot

The dispatcher selects MCP mode only when invoked with exactly one argument, mcp or --mcp; everything else is CLI or the doctor command. It stamps the package version into the environment before any other module loads, so that version reporting cannot drift from the running code. (Changed after 6.5.0: the CLI and doctor paths gained an EPIPE guard, installed on every platform, that maps a closed stdout to exit status 141; MCP stdio keeps its own lifecycle.)

run() then performs, in order: a frozen environment snapshot (on Windows, keys are sorted, upper-cased, and the first case-insensitive match is kept; changed after 6.5.0 so that later aliases win); configuration parse; logger construction; session construction; an optional initial target; transport start with a result-delivery budget; and shutdown registration. An invalid configuration prints its projected configuration message and exits 1. Any other unexpected startup exception deliberately drops its cause and prints a single SERVER_START_FAILED line, a decision that trades diagnosis for a guarantee that no internal path leaks into a client’s first contact.

Shutdown has up to four cleanup owners (transport, Android providers when present, optional observation providers when present, session), closed concurrently, and is idempotent while an attempt is in flight. A failed attempt is not cached, so a later signal retries the owners that have not yet closed.

4.2 Contracts and registration

Tools are not registered ad hoc. Each is a ToolContract carrying name, title, description, kind, Zod input and output schemas, an effects record, derived annotations, a returnsTargetContent flag and examples. The complete ordered inventory is the concatenation of 36 family arrays, and a tool whose name is missing from the effect audit table throws at construction. Catalog ordering is explicitly never allowed to select a handler: binding is by exact name.

The effects vocabulary has ten booleans: mutatesTarget, mutatesSession, writesFilesystem, launchesProcess, accessesNetwork, changesUiState, mayDiscardData, executesForeignCode, mutatesDevice, idempotent. The MCP annotations are derived from them rather than written by hand: readOnlyHint is true only when no effect is set; destructiveHint is mayDiscardData ∨ executesForeignCode ∨ mutatesDevice; openWorldHint is launchesProcess ∨ accessesNetwork. In the 6.5.0 catalog we measured, the distribution over (read-only, destructive, open-world) is: 94 tools (false, false, false), 76 (false, false, true), 23 (false, true, true), 8 (false, true, false) and 6 (true, false, false). (At fe2a398dd the first two are 93 and 77, because analyze_javascript_application now also declares a launched worker.) Only six tools in the entire surface claim to be side-effect-free: a conservative audit, since recording Evidence itself counts as mutating the session.

4.3 Two schema projections, and what they cost

Zod schemas serve two different audiences. The advertised projection is what the client reads; the canonical schema remains responsible for runtime validation. Input schemas are projected with inlined reuse, so an agent never has to resolve a local $ref; output schemas are projected with references and given a content-addressed $id of the form urn:rea:tool-output:sha256:<digest>.

This is expensive. We measured the advertised catalog directly (§13.7): 207 tools, 3.09 MB of tools/list JSON, of which 2.26 MB is output schemas and 0.69 MB input schemas, with a single tool’s input schema reaching 154.7 KB. Two environment switches change that. A compact input profile enforces a 13 KiB per-tool budget by first stripping annotation keys, then (if the result is still over budget or nested deeper than ten levels) reducing to root properties with detected types plus a sentence stating that the server still validates complete canonical inputs. An output-schema profile of off removes output schemas from tools/list on the wire only; the registrations stay canonical. Measured together, the two switches take the catalog from 3.09 MB to 215 KB.

The catalog identity reflects what is actually advertised: the digest covers each tool’s name, title, surface, description, effects, returns_target_content, annotations and both schema projections, canonicalised and hashed. In 6.5.0, compacting inputs changes tools_sha256; removing output schemas from the wire does not, because the registration did not change. That asymmetry is visible in our measurements and follows from where each switch acts. (Changed after 6.5.0: at fe2a398dd the output-schema profile is also part of the hashed tool catalog, so both switches change tools_sha256.)

4.4 Admission and cancellation

Every tool call runs inside an admission wrapper bound to the session. Admission captures the current lifecycle transition and generation, waits for any pending transition, and registers the call synchronously: before a transition can snapshot the set of in-flight calls. A call whose signal is already aborted is refused as cancelled without touching a provider.

The MCP request signal is passed to both the operation and the admission wrapper. Cancellation notifications are intercepted at the transport to release per-request bookkeeping, because the SDK suppresses replies after cancellation and the normal send path would never run. Completion requests get their own abort controller exposed through async-local storage.

We measured this directly. A function analysis was sent and cancelled 202 ms later with notifications/cancelled. No reply of any kind arrived in the following 60 s: not a result, not an error, not a cancelled code. The very next call, a session status probe, returned normally with the target still open, and the session then closed cleanly. The observation is the absent reply; that this is by design, rather than a lost message, is an inference, consistent with the SDK suppressing replies after cancellation, which the source confirms. Cancellation is therefore silent at the protocol level, and it does not fence the session. It does, however, discard warm state: §7.2 shows that a cancelled deep-decompiler request tears down the ephemeral program database, so the next query re-imports the artifact and repays the full cold-start cost. A client that wants to know what happened to a cancelled call has to ask the session afterwards; the reply channel will not tell it. This also explains why the cancelled code never appears in our outcome table (Appendix B): the projection exists for internal paths, but a client-initiated cancellation never produces a reply that could carry it.

4.5 Progress

Progress notifications are emitted only when the caller supplied a progressToken; otherwise a silent reporter is substituted. Reports are monotonic and rate-bounded at 100 ms, and the progress value counts emitted observations rather than inventing a total: a small honesty decision with a visible consequence: a long analysis reports motion, not percentage. Engine startup is the main source. The decompiler bridge reports every 10 s with elapsed time while import, auto-analysis and bridge readiness are still pending.

In our runs, 28 of the first 799 records carried notifications at all, but those 28 carried 5,162 notifications between them, progress is concentrated almost entirely in long engine startups and whole-program exports, which is exactly where an agent would otherwise see an unexplained silence of several minutes.

4.6 Delivery, and the budget that refuses rather than truncates

A successful result is delivered twice in the same message: as structuredContent and as a text rendering of the same JSON. The delivery budget is the stdio receive-buffer size minus 1 KiB of envelope headroom; the configured floor and default are both 10 MiB, raisable by environment variable.

What happens at the ceiling is the interesting part. The result is not truncated. It is replaced by a resource_constraint error whose details name the boundary, the default receive-buffer size, the budget, the lower bound on the real response size, and (crucially) a retained-Evidence reference plus a remediation path. We triggered this four times, with three tools. Two WebAssembly inspections reported a response of at least 10,488,939 bytes, a complete managed-member inventory at least 10,506,833 bytes, and a cross-version application comparison at least 10,527,313 bytes; each was refused with the same shape and an Evidence identifier through which the complete result remained reachable. The reported size is a lower bound: when the comparison was repeated in a later campaign with the budget raised to 64 MiB, the full reply was 60.7 MB, the largest single response in the study. The message states explicitly that the analysis result “was not truncated”, the distinction between a smaller answer and a pointer to the whole answer is the whole point.

Errors take a different path: they are encoded as text only, with structured content stripped at the transport, and an oversized error is itself retained as Evidence and replaced with a bounded description of where to find it.

A refusal can still carry what the run did see. Every analysis error has an optional partial-observation field, and the most important producer is late cancellation: when a provider operation is cancelled after its Evidence has been assembled, the server returns a cancellation error that carries the complete record. On the MCP path, if that partial observation is itself an Evidence record and the session retains Evidence, the server records it and the error carries a retained-evidence reference rather than inlining it, so the caller can read the finished result through inspect_analysis_view or get_evidence_bundle despite the failure. The same channel carries a complete artifact inventory whose provider cleanup failed, or extracted files whose descriptor cleanup is unresolved: the failure is reported honestly, and the observation that preceded it is not thrown away.

Finally, results that carry target bytes (strings, decompiled text, page content, script bodies, logs) are tagged _meta.provenance.untrusted_content. Exactly two tools are exempt, and an unknown name defaults to untrusted. The server’s own instructions tell the client that such content is data, never instructions.

5. The Evidence model

Figure 3. The Evidence record. (a) the layout, with the brace marking the part the identifier commits to and the two display fields it deliberately excludes; (b) how the identifier is formed, and the two measured consequences of that choice; (c) every record produced in the study, placed on the confidence × authority grid.

5.1 The record

An Evidence record is a strict object: an identifier of the form ev_ plus 64 lowercase hex characters; a nullable subject (name, SHA-256 digest, local path, format, architecture); a provider (id, name, version); a nullable analysis profile; a predicate type; the operation name; the parameters it ran with; a nullable raw result; a normalized result; a confidence of observed | derived | inferred; an authority of shipped-artifact | controlled-replay | historical-reference | external-service | analyst-inference; a nullable environment; limitations; nullable relationship coverage; locations; and evidence links.

Confidence answers how directly was this seen; authority answers who stands behind it. The pair is the calibration signal an agent needs, and it is not advisory: the verification tools in §8 refuse claims whose sources do not meet the required authority.

Four of those fields do quiet but essential work, and each was populated in our runs.

analysis_profile. The exact configuration an engine ran with, committed by digest. For a function analysis under the deep decompiler, the profile named the provider and version and then a parameter set that reads like a contract: target kind and format, architecture and the architectures available in the container, import_mode: ephemeral-source-immutable, and versioned policy names for annotations, load-image observations, function-body evidence and reference collection. The profile digest is part of the hash, so two analyses of the same bytes under different engine settings can never share an identifier. It is also the snapshot-cache key’s binding component (§6.6). Format readers that run no configurable engine leave it null.

locations. Coordinates into the artifact: an artifact path, an address, an address range, a file offset or a file-offset range. A view of a binary layout carried an artifact-path location; a Go build-info read carried both an artifact path and the exact file-offset range of the build-info blob. Because locations are hashed (§5.3), a tool that models its input by path will produce a different identifier for relocated bytes, and a tool whose locations are addresses will not.

evidence_links. The identifiers of the records this one was derived from. A view links to its single parent; a process comparison links to its two captures; a bundle comparison links to nothing because its inputs are files. Links are what make the derivation chain auditable: a verification tool can walk them, and §8.4’s authority blockers are evaluated over exactly these sources.

relationship_coverage. How complete a relationship answer is: complete, partial or unknown, plus diagnostics. A function dossier reported complete, and the diagnostic beside it qualified what complete means: only resolved call references are returned, and unresolved computed or indirect calls remain unknown. Every node in a call graph carries its own coverage block, so an agent can see which parts of a graph are exhaustive and which stop at an indirect call. When the field is missing on a caller or callee query, the session fills it as unknown rather than leaving the reader to assume completeness.

5.2 Identity is the hash of meaning

The identifier is ev_ followed by the SHA-256 of a canonical JSON projection of the record. The projection deliberately excludes subject.name and subject.local_path, and of course the identifier itself. Everything else (provider, profile, parameters, raw and normalized results, confidence, authority, environment, limitations, coverage, locations and links) is hashed.

Canonicalisation follows RFC 8785 with UTF-16 code-unit key ordering and ECMAScript number formatting, streamed so that very large results never need a single serialized buffer. Reimplementers should note three traps the study’s own tooling had to respect: key sort is by UTF-16 code unit, not code point, so a supplementary-plane key sorts before U+E000; numbers are IEEE doubles formatted by Number::toString, so -0 hashes as 0 and 1e-7 is not 1e-07; and lone surrogates are escaped rather than rejected.

A record is authenticated on parse: the identifier is recomputed from the record minus its identifier, and a mismatch is rejected as “Evidence semantic identifier does not match its record”. Validated records are deep-frozen and registered by snapshot identity, so an arbitrary freeze elsewhere cannot forge the seal.

5.3 What identity does and does not survive

Because the name and path are outside the hash, a record can be rebound to a new path, but only when digest, format and architecture all still match.

We tested this end-to-end rather than taking the code’s word. Opening a 15 KB ELF executable with the deep provider and analysing a function produced ev_cbafe2e1…; copying the same bytes to a different directory under a different file name and repeating the analysis produced the identical identifier. For a format reader whose contract takes a path as an argument, the opposite holds and must: the same bytes under a different path produced a different identifier, because the path appears in parameters, in the normalized result’s artifact record, and in the artifact-path location, all of which are hashed. Path-independence is therefore a property of how a tool models its input, not a blanket guarantee: a distinction worth stating plainly, since the hash exclusion alone invites the stronger reading.

We also confirmed that identifiers are an adapter-independent property: running four format readers through the CLI produced byte-identical identifiers to the MCP calls made earlier with the same arguments, which is what “two adapters over one set of contracts” has to mean if it means anything.

5.4 Residual unknowns

Figure 12. Residual unknowns. (a) the five statuses, which an update may change freely (each update is a revision-guarded full replacement), and what each disposition requires; (b) revisions as a hash chain, with a stale write bouncing off it; (c) what the runs actually produced, including the two refusals that enforce the authority rule.

An unknown is identified by unk_ plus the hash of its domain, whitespace-collapsed question, scope digest and, when present, its comparison conclusion scope. It is not a flag but a chain: each revision commits to the digest of its predecessor, and every write must name the expected_revision it believes is current. Statuses are open, investigating, blocked, contradicted and resolved; a resolution carries a disposition of verified, withdrawn or out-of-scope, and only verified requires supporting Evidence.

Unknowns are also created without being asked for. Every bounded process capture adds unknowns for sampled process trees, the pre-launch executable digest, the unrecorded inherited environment and unobserved network activity, plus conditional ones for unobserved filesystem paths, sensitive input and truncated filesystem or process coverage (truncated terminal output is reported as a limitation, not as an unknown). Call-path and feature-trace workflows register their coverage gaps the same way. In one small campaign a single capture produced six ledger entries without any explicit request.

We exercised the concurrency and authority rules directly. A record-then-update sequence with a matching expected_revision appended revision 2 as expected. A second write reusing revision 1 was refused with revision_conflict and appended nothing. A verified resolution citing a comparison record (which is derived with analyst-inference authority) was refused with evidence_integrity_mismatch when the unknown required controlled-replay; re-pointing the same resolution at the capture record itself (observed / controlled-replay) was accepted and verify_unknown_resolution returned valid and truthVerified together. That is the design working as advertised: the ledger will not let a comparison stand in for an observation.

5.5 Bundles

A bundle is a canonical aggregate: artifacts, providers, environments, scenarios, captures, unknown revisions and records, each sorted deterministically, with records ordered by identifier in code-point order. Parsing rejects duplicate identifiers, revision gaps, broken chains, missing references, verified resolutions that do not meet their own requirements, and dependency cycles; it then rebuilds the canonical form and requires byte equality with what it parsed.

We tested tamper rejection on an exported bundle of 25 records and 2 unknown revisions. Adding one limitation string to one record, and separately renaming one segment inside one record, both produced the same refusal: evidence_integrity_mismatch, naming the exact record index whose semantic identifier no longer matched. No partial acceptance, no warning-and-continue.

6. Sessions, providers and ownership

Figure 4. Ownership and session state. (a) the process tree, with the proof carried on each edge: a token in the child’s environment and an unchanged start time, never a bare pid; (b) the session automaton, where an unproven release lands in a fenced state that refuses later opens and external mutations until a retried cleanup succeeds. State names are ours.

6.1 One target, serialized transitions

A session owns at most one active target. Transitions (open, close, external mutation) are serialized through a chain, each capturing a generation number; calls admitted at or before a transition’s generation are drained before it proceeds. An open that finds the same target and profile with a live client takes a fast path; otherwise the previous client is retired. A failed retirement clears the provider cache but keeps the investigation records, which is the right asymmetry: losing an engine should not lose what was already established.

6.2 Deterministic provider selection

Providers are registered with validated identifiers and sorted by Unicode code point, so registration order cannot affect selection. Explicit selection fails with a specific reason: unknown provider, target unsupported, provider unavailable, or a profile-resolution error. Automatic selection evaluates every available, supporting candidate in parallel and then does something unusual: with two usable candidates it refuses as ambiguous rather than ranking them. We observed exactly this on the fe2a398dd checkout, the only version with both deep providers, when both were installed; the error text asks the caller to set the provider explicitly. There is no priority order to misremember, and no silent downgrade.

6.3 Ownership proof

A child is REA’s only if a run token minted before launch is still present in that process’s environment and the process’s start identity (field 22 of /proc/<pid>/stat on Linux) is unchanged across the check. Token checks are bracketed by identity reads; signals are delivered only to a PID whose current identity matches the one recorded at launch; and cleanup fails closed if the process table cannot be read at all.

Processes that cannot be proven one way or the other are divided carefully. An unreadable candidate that is unrelated and either owned by another user or, on macOS, a platform-binary or restricted process whose environment the kernel withholds, is reported as unverified and left untouched. Every other unreadable candidate is a failure. This is why one of our Electron captures ended in cleanup_incomplete: the runtime’s zygote processes returned EACCES on /proc/<pid>/environ, and because they shared our user id they were classified strictly rather than withheld. Re-running the same scenario with the zygote disabled produced a clean capture with the IPC observation intact, the refusal was accurate about what it could not prove, and the fix was to change the target’s process topology, not to loosen the check.

6.4 The fence, and its cost

A cleanup that cannot be verified does not merely fail the call. It is retained, and the server keeps two separate fences.

The first is the provider-client fence. When closing an analysis client fails, the pending cleanup is retried before every later open_binary and before every external-mutation call; each such call returns the failure while it persists, and the fence lifts the moment one retry succeeds. The second is the external-mutation fence. A failed cleanup from a mutation tool, such as a debugger detach, is stored apart: every later open returns that stored failure without retrying it, and it is retried only by a later external-mutation call that carries its own recovery step, for example another close of the same debugger session. Either fence blocks opens and external mutations while it holds; unrelated tools, such as format readers, keep working throughout.

We hit this repeatedly, and it is the sharpest trade-off in the system. We closed a live-debugger session three times, and all three closes failed the same way: once after the inferior had run to completion, once with it stopped at a breakpoint in main, and once with it still at its entry point, never continued. Each time the detach verification’s start-time read of /proc/<pid>/stat returned ENOENT, meaning the inferior’s process entry was already gone when the check ran, and that path, unlike the after-exit reader, does not treat ENOENT as “ended”. We did not establish what removed the inferior before the check; what we can say is that the failure did not depend on whether the inferior had exited. Each resulting cleanup_incomplete then refused unrelated open_binary calls on different artifacts later in the same campaign, four in total. Correctness-wise this is defensible: the server declines to claim it released something it cannot prove it released. Usability-wise it means one engine’s edge case can cost an agent the rest of its session: in our runs the retried cleanup never succeeded, the refusals persisted into later campaigns, and the only remediation that worked (restarting the server) is heavier than the fault. On this host we never observed a successful close of this bridge.

6.5 What an agent can see before its first call

binary_session is the only tool designed to be called before anything else, and it is the session’s whole self-description. It starts no analysis. On our host a single call returned 47.9 KB containing:

  • Capabilities by provider, each with shared limitations.
  • The deep-provider candidates with their availability and diagnostics: install directory, the headless launcher, the native decompiler binary, the Java command and the resolved engine version.
  • The current binding: null before any open, the provider, profile and selection source afterwards.
  • Run and activity state, and per-provider operation health.
  • Tool availability: all 207 tools folded into 72 groups that share the same surface, effects, annotations, availability, reason and remediation. On our host 44 groups were available, 20 were target_required (no artifact open yet), 5 were unsupported_host and 3 were provider_missing. A provider that fails to load turns its tools’ group to unavailable with the load failure as the reason, without failing the server.
  • Client features the server detected from the handshake: elicitation, roots and sampling all false for our driver.
  • Server identity: package and server version, SDK versions, negotiated protocol, client, skill, catalog counts and the three catalog digests.

The identity block also answers a question most tool servers cannot: is the server I am talking to the one I registered? A caller can pass an expected package version, catalog digest or registration path. We tried all three outcomes. With the correct version, and with the correct version plus the correct combined catalog digest, the alignment state was aligned. With a wrong version it was mcp_server_restart_required with reason package_version_mismatch; with a wrong digest, the same state with catalog_digest_mismatch. Without expectations it is unknown, and the remediation says what to supply. An agent that pins a digest therefore learns when its tool catalog silently changed underneath it.

6.6 Snapshot replay, measured

Appendix F.4 gives the cacheability rules from the source. We confirmed them against a warm session.

  • Inventory reads are deterministic, not replayed. Two consecutive list_segments calls, and two consecutive list_procedures calls, returned identical Evidence identifiers with no replay limitation. The engine answered both times, and because the answer was the same the hash was the same.
  • Function analysis is replayed, and the replay is visible. The first analysis of a function took 249 ms and produced one identifier. The second took 45 ms and produced a different identifier, because its record carried one extra limitation: “Loaded from a local REA analysis snapshot; this call did not re-run the provider.” Replay is part of the record’s meaning, so it is part of its hash. An agent comparing two identifiers can tell an engine answer from a cached one without being told.
  • Snapshots survive close and reopen. Closing the session with a snapshot path wrote a 322 KB snapshot holding one primitive entry, one workflow entry and five Evidence records. Reopening the same binary with that snapshot and repeating the function analysis returned the replayed identifier again, in 73 ms, with the subject path rebound to the current location.

7. Engine bridges

Figure 13. Starting a deep engine, as a sequence. Activation bars show when the engine process and the bridge script are alive; the blue messages are the authenticated channel. The table lists what each of the other bridges proves before it trusts its own channel.

No engine is installed by the server; each is supplied by the operator through an absolute-path environment variable and verified before use. The bridges differ in mechanism but share a pattern: hash the input into a private root, launch with a minimal and explicit environment, authenticate the channel, verify that the engine is analysing exactly the bytes we hashed, and prove teardown.

The deep decompiler bridge builds a runtime root with mode 0700 containing project, home, temp, cache, config and two descriptor files; the socket descriptor is 0600 and is deleted by the bridge after reading on POSIX. The engine is launched directly as a JVM (not through its shell wrapper) with an explicit heap, two GC threads, two compiler threads, headless AWT, and home and temp directories redirected into the private root; JAVA_TOOL_OPTIONS and its siblings are scanned, and the launch is rejected if they would override os.arch or os.name, which select the native decompiler binary. The import is read-only with an ephemeral project, and pre-scripts handle raw and 16-bit container preparation, analysis seeds and analyser options before auto-analysis runs. Before serving, the bridge verifies the engine version against the expected version and compares the imported file’s SHA-256 against the expected digest in constant time. The whole startup (root creation, launch, import, auto-analysis, connect, handshake and readiness) lives under one deadline, 330 s by default and configurable through REA_GHIDRA_STARTUP_TIMEOUT_MS, with 10 s progress reports, and requests are one NDJSON line each carrying the session token.

A second deep provider, the whole-program exporter, exists only at fe2a398dd (it is not in the 6.5.0 release) and takes the opposite approach: a whole-program export, cached under a key covering the target digest, the engine binary’s own digest, its version and the export command, published atomically by rename and evicted by LRU.

The debugger bridges are where ownership discipline is most visible. Both verify that the inferior’s standard output and error point at the caller-supplied TTY by comparing device and inode through /proc/<pid>/fd/{1,2}, bracket the check with start-time reads, and detach only when every one of those checks passes. The Rizin path additionally verifies that dbg.exitkills reads back false, issues the close, and requires that a second object listing is empty with an unchanged start time.

The GUI-attached bridges add their own protocols: a mutual HMAC-SHA256 nonce handshake over a loopback socket with a descriptor file at 0600 under a 0700 directory, a document-generation guard that refuses a command if the open document changed under it, and a bounded table of completion receipts so a dropped reply can be recovered rather than re-executed.

The format readers need no engine process in several cases (Go build info, Rust dependency sections, PE resources, managed metadata, Flutter snapshots, ZIP-family and Apple archive inventories are parsed in-process under explicit budgets) and where an external tool is required, the tool’s version banner must match an audited release and its binary is re-hashed around every run.

7.1 From an operation name to an engine call

There is no translation layer between the tool surface and the engine. The MCP (or CLI) operation name is the bridge method name: the client’s callTool(operation, parameters) puts operation straight onto the wire as the request method, and the deep-decompiler bridge switches on it directly. The admitted set is declared on both sides and must agree, and the bridge’s request queue admits one request per analysed program at a time. What an operation does inside the engine is therefore worth stating explicitly, because the mapping is where a re-implementer’s real choices live: whether a “string” is a defined-data record or a byte scan, whether a “search” is an engine query or an in-process filter, and whether a “call graph” is one engine call or many.

7.2 What the first query pays for, and what a warm one reuses

Because the bridge is launched as the engine’s last post-analysis script, the first deep query pays for the entire headless run before the bridge answers: a digest-verified private copy of the target, JVM start and import into an ephemeral project, any loader-prep and seed scripts, Ghidra’s default auto-analysis to completion, two small post-analysis repairs, and one decompiler initialization. REA runs the engine’s default analyzer set; it never enables or tunes an individual analyzer, and its only analyzer hook is subtractive, disabling exactly the analyzers a caller names through an environment variable (the committed analysis_profile records ghidra-default or ghidra-default+disabled:<list> accordingly, so a snapshot cannot be replayed under a different analyzer set). This is why §13.5’s cold-start numbers track what the binary makes auto-analysis do rather than file size, and why the capability text states that the session serves nothing until auto-analysis reports complete.

A warm query pays only the queue wait, one socket round trip, and whatever its handler walks. Three inventories (names, procedures, strings) are memoized on first use and reused by every name-selected operation; they are invalidated only by a mutation (an annotation or a rename), never by a read. The decompiler keeps its own result cache for the session, so a second procedure_pseudo_code on the same function is a cache hit while a new function is a fresh decompile. One consequence is sharp: cancelling an in-flight request tears down the ephemeral program database, so the next query re-imports the artifact and repays the full first-query cost.

8. Runtime observation and verification

Figure 14. Runtime observation. (a) one capture on its own clock, with the four bands that are recorded and the budgets that bound them; (b) the ten comparisons made without a trace specification on the same program, in three groups (eight of two byte-identical copies, two of a capture with itself), with the overall verdict outlined; mixed cells give counts.

8.1 Bounded capture

A process capture is declarative: executable, arguments, working directory, environment, filesystem observation paths, terminal geometry, timed input/resize/signal events, and four separate time budgets (timeout, idle timeout, settle, finalization). The child runs on a PTY in its own process group with the run token in its environment; a caller-supplied run token is rejected by the schema. Terminal output is captured twice (raw byte frames with bucketed timestamps, and headless-terminal renderings), each accounted separately against the output_bytes budget (1,000,000 bytes by default), and a frame that would exceed the budget is dropped whole and counted rather than silently clipped. Filesystem observation is a before/after snapshot with a shared hashing budget, and files that do not fit are recorded as explicit hash omissions.

Settlement is its own observation: after the process exits, owned groups are polled until two consecutive empty observations give quiesced. If the settle window ends first, it gives alive_at_deadline when a live member was seen during the window and unverifiable otherwise; an unverifiable token observation also gives unverifiable, and on Windows settlement is always unverifiable.

8.2 Comparison, and why “identical” is rarely the answer

Captures are comparable only when their comparison contracts hash equal. The contract deliberately excludes the executable path and arguments and redacts input data, so two different builds of the same program under the same scenario remain comparable.

Five dimensions (terminal, interaction, exit, filesystem, process) each resolve to unchanged, added, removed, changed, truncated or unknown. The overall status is derived by a fixed precedence: any truncated dimension makes it truncated; otherwise any changed, added or removed dimension makes it changed; otherwise any unknown dimension makes it unknown; only then is it unchanged. Two consequences showed up immediately in our runs and are worth stating because they will surprise users:

  1. An exact comparison can never conclude unchanged, because every capture carries automatic process-scope unknowns by construction, and filesystem effects stay unknown unless observation paths are declared. Both comparisons of a capture with itself returned unknown.
  2. Two copies of one file are reported as changed. We compared captures of two byte-identical executables (same SHA-256, different path) eight times without a trace specification. With 10 ms buckets (one comparison) terminal output diverged first, at 70 ms versus 20 ms. With 1000 ms buckets (seven comparisons) the terminal dimension agreed in five, but interaction differed in six and exit in all seven: the recorded input dispatch time (347 ms versus 309 ms in one run) and the settlement time inside the exit dimension (167 ms versus 138 ms in another) were compared at their recorded values despite the wider bucket. All eight overall verdicts were changed. The system is being precise, not wrong; but an agent asking “are these the same?” will get changed for two copies of the same file unless it either supplies a trace specification that constrains the dimensions it cares about, or reads the dimension breakdown rather than the headline.

Trace specifications are the designed answer: a partial-order or finite-trace language over selected event sources, with explicitly ignorable fields such as sequence numbers and timestamps. A trace verdict overrides only the dimensions whose sources the specification actually covers.

8.3 From run to verdict

Figure 5. From observation to verdict. A missing authority or an unobserved dimension forces unknown; an observed change yields fail; an open ledger entry blocks a pass but does not soften a fail. Nothing in the path can raise a verdict.

8.4 Verification tools hold their line

verify_reconstruction classifies each claim as pass, fail or unknown, and applies authority blockers before anything else: a behavioural claim requires observed controlled-replay sources from identical environments, a structural claim requires shipped-artifact sources (observed, or at least non-inferred for function claims), and a claim in which the same source observation appears on both comparison sides is blocked. A comparison whose source references are missing is rejected outright rather than blocked. The gates then apply in order: any blocker forces unknown; otherwise an observed changed, added, removed or contradiction gives fail; otherwise an observed unknown or truncated, or a related unresolved ledger entry, gives unknown; only then is the claim a pass. An open ledger entry therefore blocks a pass but does not soften a fail. The result carries a standing limitation that it does not establish global implementation equivalence.

correlate_static_and_runtime takes caller-declared mappings with an expected pattern and reports hypothesis, contradiction or unresolved branch: never causation; its limitations say so. The obligation ledger resolves to ready, open, failed or unknown, and the coverage evaluator to ready, partial, failed or unknown, each with reasons. In the coverage evaluator an active unknown not explicitly allowed pushes the evaluation to unknown unless a failing reason already makes it failed.

The pattern is consistent: these tools can downgrade a claim, and they cannot upgrade one. In our runs we saw a verify_reconstruction fail on a pair of byte-identical binaries precisely because the behavioural dimension included settlement state, a false alarm at the level of user intent, but a true statement about what was observed.

Every paged variant takes offset and limit, and every result carries a coverage block stating how many items were examined out of how many exist, whether the page was exhausted, and the next offset.

9.2 A view is Evidence about Evidence

This is the part that matters for the epistemic model. A view is not a convenience formatter; it is a recorded derivation. Each view result is a full Evidence record whose provider is rea-analysis-view, whose confidence is derived (or inferred for an api-surface page whose grouping templated any paths) and whose authority is inherited from what it read, and which names:

  • parent_evidence_id and parent_operation: which observation it projected;
  • parent_digest: the digest of that parent;
  • view_digest: a digest of the projection itself;
  • coverage: examined, total, exhausted, next offset;
  • the parent’s limitations, carried forward.

The coverage numbers are computed by the view at request time, not stored in the parent: total is the length of the parent collection the facet names (its assembly lines, its callers, its p-code operations, or, for pseudocode, its length in code units), examined is the slice actually returned, and exhausted and next_offset follow from the two. No engine call is made, so a page is in-memory arithmetic over a record the session already holds, which is why §9.3’s view latencies are tens of milliseconds against parents that cost seconds.

In our runs, projecting a binary layout to its mitigations facet produced a record whose own facet payload is additionally marked evidence_kind: inferred. The two labels are not duplicates and not a second vocabulary: the record-level confidence says how this projection relates to its parent (derived), while evidence_kind inside the facet says how the producer arrived at that particular field (inferred from ELF headers and flags, not read as a declared value). An agent that reports “the library is PIE with full RELRO” is therefore told twice, in machine-readable form, that it is holding an inference over a derivation.

9.3 Measured behaviour

Fifty-five view calls across the campaigns: 24 succeeded and 31 were refused (19 invalid_request, 12 unsupported_target). What the successful calls establish:

  • Projection is cheap. The 24 successful view calls ran in 8–109 ms (median 15 ms); the parents we could match to their producing call had cost 0.4–30 s to produce. Paging a layout’s sections cost 14–15 ms; reading one function’s pseudocode out of a 349 KB function dossier cost 15 ms.
  • Views validate the parent, not just the selector. Asking for a wasm view of a binary layout Evidence returned invalid_request; asking for a managed-members view of an Evidence produced at summary detail returned unsupported_target. Both refusals are typed and name the mismatch.
  • Detail level is part of the contract. inspect_wasm_artifact and inspect_managed_members accept detail: summary | complete. The collection views require the complete parent. On our corpus the complete parent for those two tools exceeded the 10 MiB response budget and was refused (§4.6), while the summary parent was accepted but then could not be paged. That pair of refusals is coherent, and it is also the sharpest usability edge we found in the whole system: for a large WebAssembly module or a large assembly, the paging path and the budget path close on each other, and the documented way out is the CLI or an exported bundle rather than MCP.
  • Retained and inline sources behave identically. The same projection taken from a retained identifier and from an inline Evidence copy produced the same view content and the same coverage block.

10. Composed workflows

Not every tool is a thin wrapper over an engine. Nine of them are composed workflows: they call several engine operations, assemble one answer, and register their own coverage gaps in the unknown ledger. They are the system’s answer to a question an agent would otherwise have to orchestrate itself, and they are where the epistemic discipline is most visible, because a composition can be partially blind in ways a single call cannot.

10.1 What a workflow adds

trace_feature is the clearest example. Given a literal query it searches strings, searches procedure names, resolves cross-references for every hit, and resolves each reference to its containing procedure. The result holds matches (typed string or procedure, each with an address and a value), references, an explicit truncated flag, an operation count, and residual_unknowns. Running it for seccomp against a sandbox library returned string hits with addresses, procedure hits, and the cross-references between them in 328 ms, over an engine session that had cost 84 s to warm.

The composition is imperative, not declarative: there is no user-visible graph, and the workflow decides its own operation order. That order splits cleanly by kind. The graph-walking workflows (trace_call_path, get_call_graph) are adaptive: they drive a frontier of procedure_callees/procedure_callers calls, stop as soon as a goal is reached, and demote a failed or coverage-incomplete node to an error or unknown entry rather than aborting, so a missed goal with open unknowns is reported as unknown reachability rather than “not reachable”. The literal and Evidence-composition workflows (trace_feature, build_call_path, trace_application_feature, the graph projections) are fixed single-pass pipelines: trace_feature, for instance, always runs search_strings then search_procedures, then one xrefs per hit and one containing-procedure resolution per distinct source address, with no branch on empty results and no budget cap. Neither kind guesses at coverage: the only thing that sets a workflow’s truncated flag is an explicit truncation report from a provider call it made. What is user-visible is the accounting. Every workflow result we recorded carries, in the same record:

  • the operation count it spent,
  • a truncated boolean,
  • a relationship_coverage block where the question involves relationships, and
  • a residual_unknowns list, which the server registers in the ledger for three of the workflows (trace_feature, trace_call_path, inspect_native_api) with required_authority: shipped-artifact and severity medium.

That last point is the design decision worth copying. A composed answer is exactly the place where an agent is most likely to over-read the result, because the composition hides which parts were measured and which were skipped. Here the composition writes its own gaps into a durable ledger that later verification calls must respect.

10.3 Failure composition

A workflow that cannot complete does not emit a partial answer as if it were whole. When the directional argument was wrong, the call was rejected by schema validation before any engine work. When a call-path traversal could not resolve a goal, it reported exhaustion rather than inventing a path. When the dossier facet an API reconstruction needed was unavailable, the boundary came back with available: false and a reason instead of a guessed signature.

11.2 Completions read the live ledger

Argument completion is declared per argument across eight kinds. The interesting question is whether completion is real, or a schema decoration that always answers empty. We tested it against a populated session; Appendix D gives the full table of eleven probes.

Completion is live. The same unknown_id argument returned nothing against an empty ledger earlier in the study and five entries once unknowns existed; evidence_id on ev_ returned nineteen; capture_evidence_id returned exactly the two process captures the session had recorded. The zero rows are equally informative: document and procedure complete against an open target, and none was open; left_manifest_id and focus_occurrence_id complete against artifact manifests, and the session held none. Completion answers from the session’s own state, which means an agent can discover what it may cite rather than guessing an identifier and being refused.

11.3 The CLI is a peer adapter, not a wrapper

The CLI exposes 153 commands over the same contracts, though not one per tool: 65 of the 207 tools have no dedicated CLI command. We measured the adapter rather than assuming parity.

  • Identity parity. Four format readers run through the CLI produced Evidence identifiers byte-identical to the MCP calls with the same arguments (§5.3).
  • Output formats. The same observation rendered as TOON, JSON, YAML, Markdown and JSONL: 56.8 KB, 62.5 KB, 67.6 KB, 68.2 KB and 62.5 KB respectively. In the tool’s own token counter, the default TOON rendering cost 15,008 tokens against JSON’s 17,467 for the identical result, a 14% saving that exists only on the CLI side; the MCP adapter sends every successful result as JSON twice (structured plus text) and errors as text only.
  • Paging without a session. --token-limit 400 returned a 1.4 KB slice of a 56.8 KB result, and --token-count returns the count instead of the content, so a caller can price a call before making it.
  • Self-description. --schema prints the command’s JSON Schema; --llms prints a machine-readable manifest.
  • Two error vocabularies, one exit code. A domain failure prints REA’s typed projection (invalid_request with issues naming the field). A framework failure prints the CLI’s own code: COMMAND_NOT_FOUND (with a suggested command), VALIDATION_ERROR (with the Zod issue list), UNKNOWN (“Unknown flag”). All five failing commands we ran exited 1; all fifteen successful ones exited 0. The CLI therefore distinguishes failure kinds in its payload while keeping the shell contract binary.
  • doctor is CLI-only. It reported healthy: true with thirteen scope checks on our configured host, each carrying a classification and, where unhealthy, a remediation string; the one failing check named the missing GUI engine and how to supply it. There is no MCP tool for this, which is consistent with its job: it answers “is this installation usable” before a client connects.

12. Evaluation methodology

Figure 6. The testbed. (a) the agent host drives two registrations of the same server and does the post-processing; the VM holds the engines, the devices and the display. (b) the 27 artifact classes, grouped by what they exercise rather than by vendor.

12.1 Testbed

All analysis ran on a single Linux VM (Debian-derived, 4 vCPU, 7.9 GB RAM) with the pinned Node runtime and operator-supplied engines: a 12.x headless decompiler, a whole-program exporter used as a second deep provider (supported only by the fe2a398dd checkout), headless Java decompilation over MCP, WebAssembly tooling, a 4.x packet dissector, a protocol-decoder suite, firmware carving and extraction tools, a Python exploitation toolkit, a JavaScript un-bundler, a GDB build, Rizin and its GUI, dynamic instrumentation, a headless Chromium, an Electron runtime and a virtual display. The agent host registered the same server twice (once locally and once over SSH) to confirm that the registration path is not part of the semantics. The server under test was the published rea-agents 6.5.0 npm package (the rea-agents-6.5.0 tag) for 993 of the 1,012 recorded calls. The remaining 19 calls (the two-provider comparison in §13.5) ran a build of commit fe2a398dd, 286 commits after the tag and the only version with the whole-program exporter provider; those 19 are counted in the 1,012. The GUI-engine attempt in §13.7 ran the same build but is not counted in the 1,012.

12.2 Harness

A persistent driver holds one stdio client against one server process for the lifetime of a campaign, reads ordered JSON campaign files, and records for every step: the request, the complete reply, every notification received while the request was outstanding, elapsed time and reply size. Steps reference earlier steps by name (a whole Evidence record, a single field, or a file read from disk) which is what made it possible to exercise tools that consume Evidence rather than paths. Progress tokens are attached per step.

Records are then classified per target by argument paths, endpoint ports, Evidence subjects and campaign step names; each target directory receives its own evidence records, step log, recovered artifacts and screenshots. Statistics and figures are computed from the same records, so every number in §13 is recomputable from the retained data.

12.3 Corpus

Twenty-seven artifact classes were exercised: ELF executables and shared libraries (C, C++, Go, Rust, static and dynamic); PE32+ native plus managed .NET assemblies; Mach-O, both universal and thinned, inside an application bundle; a 16-bit DOS container; a raw image with no container; Android packages with Java bytecode and with Dart AOT snapshots; a mobile package format from a second ecosystem; Electron applications as archives and as directories; front-end bundles with and without source maps; WebAssembly modules; deployed EVM runtime bytecode; SQLite-family databases; packet captures and HTTP session archives; logic-analyser recordings; router firmware; a core dump; and three live runtimes (browser, Electron, Node inspector). Self-built fixtures covered cases no public artifact provided cleanly.

12.4 What could not be reached, and why

Two host conditions shaped coverage. The device-control family needs a kernel binder device. On this kernel binderfs is not compiled in, so the legacy binder module has to be loaded with explicit device names, and its nodes are created owner-only; Android’s own services run under non-root identifiers and could not open them until their mode was widened. Getting there required a VM reboot and an operator-approved permission change, both done with the operator’s agreement. The GUI-attached engine’s licence was accepted by the operator, and we installed and verified its current public demo; §13.7 reports how far that got and where the vendor build stops.

12.5 Threats to validity

Single host, single operating system: the macOS-only tools and the GUI-attached engines could not be exercised, and their 13 GUI-cursor operation tools, plus the navigation-context tool composed from them, are therefore reported as refusals rather than results. The Android device was a container sharing the host kernel, not a phone; device-specific behaviour (vendor services, a real bugreport pipeline) may differ. Timing figures are from one VM under light load and are intended as orders of magnitude, not benchmarks; cold and warm runs are separated where it matters. Engine versions are pinned in the record; different versions will shift the cold-start numbers substantially. Finally, we exercised the system as an informed caller: an unassisted agent would make more argument-shape mistakes than our campaigns did, and our error distribution under-represents that.

Two observations matter more than the counts. For an agent, a malformed call is cheap (it costs a round trip and names the offending field) but 95 of them is a reminder that a 207-tool surface with deeply structured inputs is itself a usability surface, which is precisely what the compact-schema profile in §13.8 addresses from the other end.

13.3 Evidence identity and integrity (RQ2)

Summarising the tests already described: identity was stable across relocation and renaming for provider-backed analysis and across the CLI/MCP boundary; it changed, correctly, when the path was part of the modelled input; it changed when any hashed field changed; and bundle tampering was rejected at the exact record, in both the “add a limitation” and “rename a field value” variants. The ledger’s optimistic concurrency refused a stale write, and its authority requirement refused a resolution backed by a derived comparison while accepting the same resolution backed by the underlying observation.

The decompiler’s cold start is a function of what it has to analyse, not of file size alone: 14 s for a 512-byte raw image, 19–26 s for a 31 KB 16-bit executable, 28–45 s for a 15 KB ELF, 84 s for a 128 KB shared library, 58–102 s for a 199 KB mixed-mode PE, 275 s for a 0.97 MB C++ executable, and 827 s for an 8 MB Swift Mach-O. The startup deadline covers import, auto-analysis, bridge and readiness; at its 330 s default this cold start would have been refused as provider_timeout, and it succeeded only because our testbed raised the deadline to 1,200 s.

The two-provider comparison on the same 15 KB ELF (19 calls on the fe2a398dd checkout, since 6.5.0 has no whole-program exporter provider) is the clearest statement of the trade-off available anywhere in our data. The whole-program exporter opened in 1.2 s, answered an overview in 4.0 s, analysed the main function in 3.8 s, and answered the second function in 24 ms from its export. The classical decompiler opened in 30 ms but spent 46.7 s on the overview that forced its auto-analysis, then answered a function in 0.7 s. One pays up front and amortises; the other pays once, more heavily, and is substantially richer afterwards: the resulting dossiers differed by an order of magnitude in size. The server does not choose between them, and refuses to guess when both are present.

13.6 Response size, and the two directions of the budget

The reply direction has a graceful ceiling (below). The request direction does not, and we bracketed where it fails. We sent single tools/call requests padded to precise sizes. Every probe up to and including 10,485,760 bytes (10 MiB; probes at 1, 4, 8, 9, 9.9 and 10 MiB) received a normal typed reply, in our case the expected schema rejection for the padding field, in 29 ms at 1 MiB and about 2 s at 10 MiB. A request of 10,590,618 bytes (10.1 MiB) received nothing: the server closed the connection without a reply. We did not probe sizes between the two, so the exact limit lies somewhere in that 100 KiB interval. Requests of 11, 12 and 16 MiB were also unanswered, and for those the client’s own write failed with EPIPE.

We first encountered the boundary unintentionally: comparing two 31.8 MB (30.4 MiB) Evidence bundles by passing them inline produced a 63.7 MB request that killed the driver’s connection mid-campaign. The systematic probes above were designed after that observation. The tool’s own contract takes bundle paths, not bundle contents, and with paths the same comparison completed in 13.3 s. The design point is real, though: the 10 MiB stdio buffer applies in both directions, the server has a careful typed refusal for oversized replies (with a retained-Evidence pointer), and no refusal at all for oversized requests. An agent that inlines large Evidence into a tool argument gets a dead connection instead of an error it could act on.

The largest successful reply in the study was 60.7 MB, delivered only because the budget had been raised to 64 MiB for that campaign. At the default 10 MiB, the same call refused with resource_constraint and a retained-Evidence reference. Nine tools produced replies above 2.8 MB: cross-version comparison (60.7 MB), semantic tracing (15.4 MB), function dossiers (8.6 MB), WebAssembly inspection (6.5 MB), Swift type analysis (4.8 MB), artifact inventories, managed member inventories, managed application-graph projection and symbol listing (2.85–3.2 MB). For an agent, these are the calls where the paging and view tools exist for a reason: the system’s own guidance is to discover retained records in summary form and then project a selected view, rather than ask for everything.

13.7 An engine that installs, verifies, launches, and still cannot be used

The GUI-cursor family is the one group of tools we could not reach, and every layer except the last worked. On the fe2a398dd checkout we installed the vendor’s current Linux demo and let the server verify it: the signed package’s SHA-1 matched the feed, its detached PGP signature verified against the primary fingerprint REA pins in its source, and the installed launcher’s SHA-256 matched the feed. REA’s doctor then caught a real host-drift problem on its own: the demo needs GLIBC_2.38 and the host had 2.36, so we moved the installation into an Ubuntu 24.04 container, where the version check passed. REA’s display probe selected a private direct display, the engine launched under it, REA’s helper accepted the registration dialog, and the target was fully analysed (fifty labels under the vendor’s “Demo version” watermark).

It stops at the bridge. REA drives the engine through a Python script handed over with -Y, and the engine’s log answers Cannot launch script ".../bootstrap.py". The document is analysed and open, but the bridge never loads, so readiness never arrives and the call fails with provider_timeout. We reproduced the refusal without REA, handing the same engine a two-line script of our own; supplying a Python 3.9 runtime changed nothing, and the demo ships no scripting plugin. The finding is therefore precise, and worth separating from a bare “unavailable”: the server’s install verification, host-drift detection, private-display orchestration and demo-dialog automation all work against the current vendor demo, and the vendor demo will not execute the script the bridge is made of. A licensed build with working scripting should complete the same campaign unchanged, which is a statement about the vendor, not the design under study.

13.9 Composition (RQ5)

The verification layer behaved as specified in every case we could construct. It refused to let a derived comparison satisfy a controlled-replay requirement; it produced unknown rather than pass whenever a related unknown was unresolved; it reported a behavioural fail for byte-identical binaries, twice, because the capture comparison each claim cited reported its dimension (exit in one run, terminal in the other) as changed from timings that genuinely differed (§8.2); and the correlation tool reported a hypothesis rather than a cause. We found no path by which a weaker source silently satisfied a stronger requirement.

The honest counterweight is that this strictness has a usability cost, and the cost is not evenly distributed. The process-dimension unknown is unavoidable by construction; the sensitivity to unbucketed dispatch and settlement times surprises; the cleanup fence blocks every later open in the session for one engine’s edge case. An agent using this system well needs to read dimension breakdowns rather than headline statuses, and needs to know that changed and unknown are frequently statements about the observation apparatus rather than about the artifact.

14. Discussion

14.1 What the design buys

Three things, concretely. Calibration: an agent reading a result knows whether it is holding a byte-level fact, a decompiler reconstruction or an inference, without having to infer it from prose. Re-citability: a result can be referenced later, compared, exported and re-imported, with tampering detected at the exact record. Bounded failure: when something cannot be done, the system says which class of thing failed and what to do next, and keeps whatever partial observation it already had.

14.2 What it costs

Latency at cold start, which for large artifacts is minutes and in one case fourteen minutes. Size, because self-describing results are large and the honest response to an oversized result is a refusal plus a pointer. Strictness, which produces unknown and changed where a human would say “same”, and which in the cleanup fence case converts a local failure into a session-wide one. Surface, because 207 deeply typed tools cost 3.09 MB of advertised schema by default, and 95 of our calls died on argument shape before reaching REA’s own handlers.

14.3 Where the refusals are over-broad

Two cases stand out from our runs. The session-wide cleanup fence is correct in its claim but disproportionate in its scope: refusing to open an unrelated artifact because an earlier debugger detach could not be verified protects a guarantee that the unrelated open does not depend on. And the detach path’s treatment of ENOENT as “unverifiable” rather than “ended” (when the sibling after-exit reader treats it as “ended”) makes an ordinary, expected sequence (debug a program, let it run to completion, close the session) fail by default. Neither is a soundness bug; both are places where the policy could distinguish “cannot prove released” from “provably gone” without weakening anything.

14.4 Lessons for agent-facing tool design

  1. Put the epistemic status in the data, not the prose. Confidence and authority as enumerated fields let downstream tools enforce what prose can only suggest.
  2. Make identity content-addressed, and be explicit about what is in the hash. Our relocation tests show that users will read “path is excluded” as a stronger guarantee than it is whenever the path is part of a tool’s modelled input.
  3. Refuse rather than truncate, and leave a pointer. A refusal carrying a retained-Evidence reference is strictly more useful than a silently clipped answer.
  4. Progress without percentages. Reporting motion and elapsed time during a 14-minute analysis is honest; inventing a completion fraction is not.
  5. Advertise less than you validate. The 14× catalog reduction with unchanged runtime validation is nearly free, and the default should probably be the compact one.
  6. Scope your fences. A cleanup guarantee should fence what depends on it.

15. Transfer to security-research agents

The mechanisms in this system are not specific to reverse engineering. They answer a problem any agent has when it acts on what it reads: distinguishing what was seen from what was guessed, and refusing to let the second masquerade as the first. For an agent that hunts vulnerabilities, where the cost of over-claiming is a false report that wastes a human triager or a maintainer, that is the central problem. This section maps the design onto such an agent. Every row is a mechanism this paper measured; the transfer is an argument, not a second system we built.

The relationship_coverage row is the one most missing from current tooling. A decompiler or disassembler hands back a call graph and asks the reader to trust it; REA attaches per-node coverage and states plainly that unresolved indirect calls are unknown. A reachability analysis that consumes such a graph can tell “the target is unreachable” apart from “the target might be reachable but an indirect call blocks the proof”. That is exactly the distinction a vulnerability-reachability claim has to make, and exactly the one a coverage-free graph erases.

15.2 A pipeline the model implies

Laid out as a finding pipeline, the confidence and authority algebra assigns each stage its honest label, and the verification gate (§8.4) is what stands between the pipeline and a confirmed report:

The gate is not advisory. In our runs the verifier refused to let a derived comparison satisfy a controlled-replay requirement, produced unknown rather than pass whenever a related unknown was open, and reported a behavioural fail for byte-identical binaries because their recorded behaviour genuinely differed (§13.9). Those are the three refusals a triage-ready pipeline needs, and they are the ones a pipeline built on bare tool output cannot make.

15.3 The failure mode it rules out

The value is clearest stated as what it forbids. Current vulnerability-report pipelines routinely commit three errors, and each is one this design refuses by construction: promoting a static scanner’s pattern match to a “finding” (blocked, because shipped-artifact reading cannot reach verified); treating a single reproduction as a universal exploit (blocked, because the environment is pinned into the identity, so an un-pinned claim is a different, weaker record); and merging crashes from different configurations into one bug (blocked, because the analysis_profile digest is part of the identifier). An agent built on this algebra does not need discipline to avoid these; the algebra withholds the verified label until the evidence for it exists.

16. Limitations of this study

This section lists limitations of the findings themselves; the methodology threats (single host and operating system, container-not-phone, informed caller, timing variance) are in §12.5 and are not repeated here.

All 207 tools were called; 29 never succeeded, so our account of those is through their refusal paths and source, not their results. Fourteen (the 13 GUI-cursor operation tools and the navigation-context tool built on them) depend on a GUI engine we installed, verified and launched, but whose demo build refuses to run the bridge script (§13.7); nine need a macOS host; four need a commercial decompiler we did not license; one is the debugger close discussed in §6.4; and one, the device bugreport, failed for a reason we did not resolve.

The self-testing apparatus was exercised only in part (Appendix G): two domain suites and two MCP boundary suites, not the full suite or the real-engine lanes. Every campaign drove one call at a time, so we did not measure interleaved in-flight calls, admission under contention, or the snapshot cache’s eviction behaviour; those are described from source only. Finally, this paper describes mechanism and measurement; it does not evaluate whether the analyses the system returns are correct, which would require ground truth we did not have for most of the corpus.

17. Conclusion

The system studied here makes an unfashionable bet: that an analysis tool for agents should spend bytes, latency and strictness on saying exactly how much it knows. The bet is implemented consistently, identity is the hash of meaning, unknowns are a durable ledger rather than a log line, cleanup is proven rather than assumed, and verification tools can only ever downgrade a claim. Our measurements say the bet is mostly paid for: all 207 tools were exercised and 178 produced calibrated results on one ordinary host, tampering and stale writes were rejected exactly where the design says they should be, and every failure we provoked came back as a typed refusal with a next step rather than as a confident guess.

It is not free. Cold starts reach fourteen minutes; the default advertised catalog is fourteen times larger than it needs to be; and the strictest guarantees occasionally fence more than they must. Those are engineering costs with engineering answers, and three of them are already configuration switches. The part that is not a cost (the part worth borrowing) is the shape of the result: a record that names its producer, its parameters, its subject by digest, how directly it was seen, who stands behind it, and what it still does not know.

Appendix F: Mechanism reference

This appendix records the mechanisms behind §4–§8 in the compressed form a re-implementer needs. Every entry was read from the source at the rea-agents-6.5.0 tag unless marked as fe2a398dd-only; entries our runs exercised directly are marked (observed).

F.1 Error projection

The closed set is twenty codes: invalid_request, access_denied, artifact_changed, unreadable_output, capability_unavailable, unsupported_target, provider_unavailable, provider_timeout, resource_constraint, cancelled, artifact_integrity_mismatch, artifact_operation_failed, evidence_integrity_mismatch, truncated, process_capture_failed, cleanup_incomplete, revision_conflict, configuration_invalid, target_unavailable, execution_failure. Categories are a separate closed set of ten. An incomplete cleanup takes priority over every other code, which is why a debugger detach failure presents as cleanup_incomplete rather than as the underlying provider error (observed). Retryability is a property of the code plus the resource: a capacity constraint is retryable, a transport constraint is not: the refused 60 MB comparison therefore advertises itself as not worth retrying unchanged (observed).

The projection is mirrored by a strict discriminated union in the schema layer and generated into a published JSON Schema, so a client can validate a refusal as rigorously as a result.

F.3 Session lifecycle invariants

  • Transitions are serialized; each captures a generation, and calls admitted at or before that generation are drained before the transition proceeds.
  • A re-open of the same target and profile takes a fast path only if the retained client is live; liveness means an operation-health snapshot of idle or busy; any other snapshot state counts as not live, and a health probe is used only when the client reports no snapshot.
  • A failed open retires the provider cache but keeps investigation records.
  • A pending provider-client cleanup is retried before every open and every external mutation, and its failure is returned rather than swallowed. A failed external-mutation cleanup, such as a debugger detach, is returned by every later open and retried only by a later external-mutation call that recovers it (observed: the refusals persisted across later campaigns). In both cases the fence lifts once a retried cleanup succeeds.
  • An external mutation is refused while the deep decompiler is active, because rebinding would discard its in-memory edits.
  • A declared artifact-mutating capability invalidates the snapshot before dispatch, on the grounds that a failed reply cannot prove a dispatched write rolled back.
  • close_binary clears the session records, which is why a retained-Evidence reference stops resolving afterwards (observed); the documented route to keep them is export followed by import.

F.4 Snapshot replay

A result is cacheable only if its operation is non-stateful, non-mutating, not live, does not write the filesystem unless its policy is snapshot, does not change permissions, and names a document or address where the operation requires one. Keys are query_ plus the hash of target, binding, operation and parameters, with the target path excluded from the projection. A replayed result adds a limitation stating that the provider was not re-run, and rebinds the subject path. A snapshot cannot be exported once analysis metadata may have changed; the recovery text tells the caller to export the bundle, close without a snapshot, and reopen.

Appendix G: Self-testing apparatus

The project tests itself at seven declared depths (module, composition, boundary, MCP boundary, acceptance, conformance and evaluation) with layering rules stating that domain tests start no processes and that only acceptance tests assemble the full runtime. Roughly 500 colocated unit test files sit beside the sources; the boundary suite is the largest single body at around 726 test files.

Two parts are unusual enough to note. First, fault-injecting fakes: the decompiler fake alone implements about eighteen failure modes, including a dropped first connection, a wrong identity, fragmented framing, an oversized result, a contradictory reply, a hang after start and an analysis timeout. The fakes exist to test refusal paths, not success paths. Second, separate real-engine lanes: roughly a hundred verification scripts each require only their own host tools, check prerequisites early, and are forbidden from implying coverage they skipped, so claims about real engines are explicitly not made by the unit suite. Mutation testing runs against named syntax owners in the reverse-engineering and debugger adapters, with a second configuration that runs the full semantics suite against every mutant of the GUI-bridge expressions and debugger timeout declarations.

An agent-experience evaluation runs eleven scenarios through an external agent CLI in a disposable home directory and grades them on exit status, correct first tool, zero repeated calls, zero validation failures, a required tool subsequence, and either a factual-correctness pass or an epistemic cue together with answer heuristics. Closed fixture claims are graded against an oracle and against authenticated successful Evidence: an Evidence identifier alone is not accepted as proof.

Appendix H: Harness record format

Each retained record is a JSON object with: sequence number, campaign step name, tool or raw method, the arguments as sent, the complete reply, the notifications received while the request was outstanding, elapsed milliseconds and reply size. Campaign steps may reference earlier steps in three ways (a whole Evidence record, a single field by path, or a file read from disk) which is what allowed tools that consume Evidence objects to be exercised without hand-copying megabytes of JSON between steps. Classification into per-target directories uses argument paths, endpoint ports, Evidence subjects and campaign step names, with explicit overrides for steps whose referenced Evidence mentions another target’s paths. The driver also supports a per-step cancellation probe, which sends notifications/cancelled for its own request after a set delay and records whether any reply ever arrives (§4.4).
